## Outcome and existing authority

A person can undo an AI-origin task creation only while the task has never acquired persisted use. The task, original creator, source links and creation notice remain truthful history. Its exact link opens read-only reverted details. Existing contributions and later work are never removed.

This is already required by #154 AC-3, F-017/UI116-3, foundation §§8.3–8.8/8.12/8.16/10, and the accepted `docs/development/task-discussions.md` and `task-discussions/2026-09-30-design-review.md`. Those records explicitly require a retained tombstone, `task.creation_reverted`, current authority, trusted AI origin, expected version, absence of persisted use under the contribution task lock, no receipt resurrection, and delayed-assignment suppression. F-016/F-019 current connection/runtime/grant and actor rules remain in force. This plan supplies the missing concrete eligibility and persistence seam; it does not weaken the parent contract.

## Proposed acceptance criteria (five; independent acceptance required)

**AC-U1 — trusted origin and current actor authority.** One immutable command `{clientCommandId, expectedVersion}` targets an exact work ID. Current project write is required at effect and receipt replay. Origin is established only by server-native agent creation or a committed proactive-comparison proposal-use binding, never client flags, text, source labels or guessed authorship. Proposed human authority is the actual human task creator, current human task assignee, or current human owner of the genuine creator-agent, additionally subject to current project write. An agent may revert only its own native-created task under a new exact `work.creation.revert` standing grant (execute/plan), current bound connection/runtime/audience and the same task predicate; ordinary `work.update` grants do not authorize it. A proposal's AI owner does not gain task authority merely by having produced the suggestion. Unsupported/unowned provenance fails closed. Read-only eligibility exposes bounded reason codes without private helper, grant or owner details. **Verify:** actual human A/B sessions, genuine server-derived agent, trusted human acceptance of AI proposal, unauthorized writer/viewer, revoked owner/connection/grant and changed command UUID payload; real API/MCP composition, not an injected “agent” browser field.

**AC-U2 — atomic “never used” eligibility and races.** New creations capture an immutable creation baseline and trusted origin in their creation transaction. Baseline owner/source/related provenance is permitted; later changes are not. Undo requires the exact unchanged produced task version/post-state, no discussion binding/message of any valid kind, result, decision/parking, dependency in either direction, handoff/claim/request/checkpoint/live session, PR/task binding, later link or saved doc mention, or other successfully persisted task-targeted use. A monotonic task-use latch survives later removal/replacement of related data. Targeted private/helper execution or saved proposal/reference use counts without turning its contents public; plain reads, temporary drafts and in-flight uncommitted typing do not. Older tasks without reliable complete use history are `eligibility_unknown`, never guessed unused or rewritten. Every successful relevant writer locks the complete sorted affected task set and either marks use atomically or rejects a reverted task. Undo and first use serialize: exactly one wins; the loser has no partial effect. Failed/rolled-back attempts mark no use. **Verify:** real PostgreSQL two-transaction races for contribution, result, link, dependency, doc save, decision, live/PR target and handoff where composed; remove dependency/mention then undo still refuses; rollback leaves eligibility unchanged; pre-feature historical tasks remain unchanged/refused rather than reconstructed.

**AC-U3 — retained history, exact durable retries and no resurrection.** Commit one read-only creation-reversion marker, version increment, append-only `task.creation_reverted` notice with actual reverter/time, durable receipt and identifiers-only stream invalidation together. Original task, creation notice, author/time, sources, proposal binding, plan intent and creation receipts remain. No contribution, result, dependent task, discussion, attachment or source is deleted. Same UUID/material yields the exact same reversion IDs after restart/current reauthorization; changed material conflicts. Every HTTP-cache/core/helper/proposal/plan/MCP creation replay after undo must return a truthful historical projection or typed terminal reversion/stale conflict, never an active original success, new task or new notice. Proactive proposal stays used; no automatic revival or replacement task. **Verify:** cached and post-cache creation replay, lost-response/restart replay, source/actor/ID comparisons and injected rollback after each state/notice/receipt write; no success UI or public partial event on failure.

**AC-U4 — one useful action and truthful consumers.** Server-derived eligible tasks expose “Undo task creation” in existing Details with reusable command identity, clear pending/error state and recoverable draft/files/refs on refusal. Success invalidates the same task/notice across Conversation, Tasks, Map and Agents. Original and reversion notices stay compact and chronological; both exact links resolve to read-only history, retaining source identity and genuine actors. Reverted tasks are excluded from active board/list totals, assigned/helper queues, map active task counts, task selectors and new automation/coordination/live/PR targets. Historical direct reads, existing references, export and Return/inbox history identify them as reverted without dead links or misleading fresh action. Delayed assignment generation and queued dispatch recheck lifecycle and suppress a fresh assignment; already dispatched notifications stay historical. **Verify:** two-account actual browser journeys, all four surfaces, late response/revalidation and delayed generator/queued delivery tests; separate neutral screenshot review for desktop/phone compact notice and read-only Details. Screenshots do not prove interactions or physical devices.

**AC-U5 — compatible migration and pinned integrated evidence.** Use an additive reserved migration with scoped FKs/checks, new lifecycle/baseline/use/reversion/receipt facts, exact schema ledger and historical export shape. No backfilled notices, inferred origin/use history, author changes, task deletion or manual ledger edits. Guarded pre-use reversal must be lossless and refuse unrepresentable new history after use; paired DB/files backup plus matching image restore must be tested without calling normal create commands or claiming an absent import API. Required regression paths run in an isolated Docker stack and are independently reviewed at one pushed source pin; failed/unavailable checks remain explicit. Parent #154 remains open until its full integrated AC-1–AC-5 outcomes pass. **Verify:** actual old-data migration comparisons, forward/restart, both relevant sparse/composed manifest orders, reversal refusal and paired restore, full application build/type/lint/API/SQL/UI checks and fresh independent candidate evaluation.
