## Verdict

Accept the proposed common persistence seam for implementation, with the integration requirements below. `prepare(ids)` gathers project identities, takes distinct ascending existing task-graph advisory locks, then one complete ascending work-row `FOR UPDATE` pass. `lockPrepared(ids)` takes only that task pass after the caller owns all upstream fences. The returned fence closes over its retained ID set; `mark(subset)` refuses IDs outside it and applies `COALESCE(firstPersistedUseAt, clock_timestamp())` in the same caller transaction without another task pass. Missing/reverted task checks happen under retained rows. Rollback therefore rolls back the latch. No authorization, new transaction, receipt store or event flush is introduced. Ordinary old active tasks may still be used; this must not infer an Undo baseline for historical rows.

## Required amendments at callers before public behavior

1. **One complete pass, no late graph acquisition.** Discover and normalize every task before taking any task, coordination or conversation lock. `prepare` is only for callers with no previously held task/domain rows. Existing graph owners use `lockPrepared` once, at their existing sorted task-pass site. A documented precondition is legitimate for this internal storage port, but repository wrappers must not secretly call `prepare` after a caller already locked a task. Repeating a graph acquisition after task locks can deadlock with another transaction, even if one particular advisory lock is reentrant. A retained fence does not authorize extending its task set.
2. **#153 must replace its existing task-pass site.** `coworkUnitRows.lock` currently owns connection-slot locks, discovers the requested unit plus claimed units across projects, invokes `prepareTaskLocks`, then locks ascending `taskId + lineageTaskId + dependency IDs`, followed by unit rows. Use the common `lockPrepared` at that one pass and carry its fence into the actual conditional save; do not add a second pass inside `requireEligible`, checkpoint validation, or after unit locks. Unit creation, enqueue/checkpoint and publication need all canonical unit/lineage tasks and all actual work-typed source/target/criteria IDs, including task ownership behind bound result/message/PR sources. Current source/material/binding/command fences must precede graphs/tasks. Mark only successful persisted conditional outcomes; an exact replay, rejected claim, pure ACK and observation do not create use.
3. **Live ordering needs explicit refactoring.** At e2, `requireLiveContext(..., lock=true)` already takes a work row `FOR SHARE`; `withAdmission` and `present` take the live-session row before context/source work rows. Inserting `prepare` after these calls violates the accepted new order. Locate the session/context and complete anchor/source task set without work locks, retain applicable authority/material/source locks, take common graph/task fence, then lock/revalidate the same session and perform the persisted effect. Recheck located identities after obtaining downstream rows. A replay or read/page operation never marks use. New persisted live session, admission/contextual use or presentation marks only the actually used retained tasks.
4. **Documents must include removed and replacement mentions.** Under the existing doc/material lock, gather the previous saved work targets and all replacement saved work targets before the common pass. Keep both until the new version/link replacement commits, then mark the used existing targets in that transaction. `replaceMentions` currently deletes old links; deriving the task set only after this deletion loses the removed set. Read/preview resolution never marks. `addSection` currently links a result/decision source before its body no-op return: an actual new saved source link is still a persisted effect, while an existing-link conflict/no-op is not a new use. Resolve any actual work associations behind such persisted sources before locks.
5. **All writer identities, not just the primary task.** Include both work endpoints of object links, old and replacement dependency targets, conversation-bound and referenced tasks, result/decision targets, saved private helper/proactive contexts, and actual PR task targets. GitHub currently pins provider credentials and binding before task persistence; keep those upstream and take graph/task fence before saving the target link. Do not infer source targets from untrusted client flags, missing rows, or a truncated list. No new task's own initial baseline/provenance link should mark it; links to pre-existing tasks mark those existing tasks.
6. **Lifecycle admission and historical replay stay distinct.** Reject a new persisted target/use of a creation tombstone under the shared retained task lock. Keep exact creation/Undo receipt replay and permitted history observation available through their existing current authorization and durable receipt path; they must not resurrect a task, mark new use, or be misclassified by unconditional new-use admission. All mark errors must abort the caller transaction; callers cannot swallow them and commit the effect.
