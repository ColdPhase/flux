# Project GitHub App integration (#74)

Status: auth/binding/link/inbox architecture independently accepted, 2026-09-30,
with the conditions in [the review](2026-09-30-independent-design-review.md). Implements CO-3 and CW-4. Existing issue acceptance
criteria remain unchanged. This contract describes the first coherent runtime
slice and its integration seams; partial implementation does not complete #74.

## Authority and connection

GitHub.com is the first supported provider; Enterprise/GitLab/Gitea are pending.
The operator registers a GitHub App with metadata, pull requests, checks and
commit statuses read-only; Issues read-only is additionally required by GitHub
for the PR conversation `issue_comment` subscription (primary docs checked
2026-09-30). Reading this event never imports/synchronizes GitHub issues.
No Issues write, contents write, code execution,
automatic approval or merge authority. Configure exact callback/webhook URLs.
A Flux login remains separate from a GitHub App user authorization, its
installation and an individual project-to-repository binding.

Each human completes an OAuth web flow with one-use random state bound to the
Flux user, auth session and project, 10-minute expiry and PKCE S256. The callback
rechecks the same live Flux session and current project access before storing an
AES-256-GCM encrypted provider credential. It never trusts installation_id from
an installation redirect. Each project manager selects an installation and a
stable repository ID from the user's currently accessible App installations and
repository list; provider GET verifies selection under the current user token.
No global current repository, no automatic expansion on newly installed repos.

Every private facts read and link operation rechecks the current Flux reader's
own GitHub App user token and current repository/installation access. A binding
manager's token does not grant all Flux readers GitHub access. Workers reconcile
on behalf of the disclosed standing-rule author and recheck their current Flux
write and repository access. Expiring tokens rotate under a credential row lock;
uncertain refresh fails closed and requires reconnect, never retries an expired
refresh blindly. Account/app/installation/repository revocation stops effects.
Secrets, raw OAuth codes/state, request authorization and private webhook bodies
never appear in exports, models, domain events or error logs. Reconnection may
restore access to retained history; restored/imported connections are disabled
until verified again.

## Stable bindings and verified PR links

A binding contains workspace/project, provider host, installation ID, immutable
repository ID, original verified owner/name and the authorizing human. Names and
URLs are display/navigation facts; correlation always uses stable IDs. A native
Flux task links to one or more verified pull requests through the binding and
stable PR ID plus number, with required-output or related role. The same PR may
be linked to separate authorized tasks/projects; no Flux context is sent to the
provider or shared between bindings. CLI-created PRs are resolved with the same
provider GET verification before linking; #42 alone never resolves globally.
Keep original provider actor and timestamps distinct from the Flux linker.

## Durable admission and reconciliation

Webhook raw bytes are size-limited and validated with X-Hub-Signature-256 HMAC
and constant-time comparison before parsing. Store delivery GUID, event kind,
SHA256 body digest and signed payload durably before returning 202. The same
GUID and body is a no-op; a changed body under that GUID is rejected. Snapshot
one independent processing row per matching active binding, keyed by delivery
and binding. One failed binding cannot roll back another. Installation/user
revocation deliveries are applied to all matching credentials/bindings rather
than treated as work comments. Processing rows survive server restarts and have
bounded exponential retries and visible pending/unavailable state.

Never use old webhook content as current PR/CI truth. Each relevant delivery
triggers a bounded GET of already linked PRs/reviews/checks/statuses using the
current verified token, stable repo/PR identity and current SHA. Overlapping
reconciliation serializes per binding and link. Thus redelivery/out-of-order
notifications converge to the provider's current state; changing SHA stales
prior assessments. Gap recovery only enumerates known binding/link rows, never
a global repository scan or an LLM poll. Only supported linked-object event
kinds enter the bridge; arbitrary external comment text is untrusted evidence.

CW-4 bridge records remain a separate durable outbox with provider delivery,
binding, link, target task, current head and causal correlation. #153 consumes
an explicit port under its current connection grants/subscriptions. Until that
adapter exists, show pending integration; writing an outbox does not prove local
client delivery/wake. Requests and echoed provider updates share correlation;
no automatic work creation, audience expansion or duplicate GitHub comments.

## Disclosed deterministic task rules

A human with current task write authority explicitly enables a rule at a pinned
native task version. The rule records its author, required PR links, expected
work version and active/suspended state. It never reassigns or changes audience.
All required output links count; related links cannot drive stages. Existing
native statuses remain unchanged. PR opened can move open to in_progress; a
current non-draft PR with current successful required checks reports a separate
ready-for-review execution state while retaining in_progress;
failed required checks can move to blocked with a sourced reason. Closed
unmerged is a blocked output, not completion. Do not override parked, done or
not_pursued work. A concurrent manual task edit causes a version mismatch and
suspends the rule before another automatic effect; resuming requires an explicit
new expected version and current author authority.

Merged/green alone never sets done. The slice records completionCandidate only
when every required link is merged with current verified checks, then leaves
native acceptance to the ordinary task/result criteria and #153 review contract.
Automatic completion remains pending until a native acceptance gate can prove
all current task/device criteria at the exact task/result version. No invented
criteria-satisfied flag is exposed to webhook callers. A current head invalidates
old SHA review facts; Flux assessments never replace eligible GitHub approvals,
checks, unresolved review threads or protected merge gates.

## Primary sources checked 2026-09-30

- [GitHub App user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app): provider documentation says user tokens are intersected with user and app permissions, supports PKCE S256 and current installation/repository checks. This is a vendor contract, not observed real installation evidence.
- [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation): installation tokens can be narrowed by repository and permission. This implementation uses user-token intersection; optional broker identity is a separate future grant.
- [Signature validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries): HMAC-SHA256 over exact raw bytes with the configured webhook secret.
- [Webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks): queue work and return promptly; treat delivery IDs as deduplication keys and recover failed deliveries explicitly.
- [Current installation API](https://docs.github.com/en/rest/apps/installations?apiVersion=2026-03-10) and [pull request API](https://docs.github.com/en/rest/pulls/pulls?apiVersion=2026-03-10): use fixed GitHub.com HTTPS origin and pinned X-GitHub-Api-Version 2026-03-10; verify response immutable IDs and current head.

Design inference: intersecting each reader's own user token avoids leaking private
repository facts to a Flux-only project member. Fetching current known objects
rather than replaying payload state avoids timestamp ambiguity and stale SHA
completion. The cost is an explicit GitHub authorization step and bounded API
reads; provider outages are shown truthfully and cannot make task success.

## Concrete first-slice limits

The first provider adapter requests only the documented read endpoints, uses
10-second request timeouts and rejects redirects. Installation/repository lists
are paginated explicitly; verified binding selection never treats a truncated
page as an authorization proof. Check/status snapshots keep their actual provider
name, creator App/context and source timestamp. Their green aggregate is an
execution hint, not a statement that branch protection permits merge. Required
checks must be explicitly selected by the rule (including the producing App ID
where available); absent/pending/skipped/neutral checks do not silently satisfy
such requirements. Required GitHub approval eligibility is left to GitHub.

A supported webhook event is a reason to fetch current facts, not an instruction
or an authorization grant. Issue comments require a pull_request object plus an
already verified link; issue-only activity never imports tasks. The bridge keeps
provider object/review/comment IDs and exact SHA references without copying
arbitrary text into a command. Installing an App alone never creates Flux work.

The standing rule snapshots all required link IDs. Adding/removing a required
link suspends that rule until explicitly resumed, so a late extra repository
cannot be ignored. Related-link changes do not authorize work. A rule captures
the author's provider authorization generation; reconnecting as a different
GitHub account cannot silently transfer the old standing rule to that account.
OAuth token refresh rotates credentials within the same authorization generation.
A fresh authorization requires explicitly resuming/rebinding affected authority.
Encrypted credential envelopes bind the Flux user/provider/generation as AEAD
associated data; copied ciphertext cannot become another user's credential.

The OAuth callback consumes its state in a committed step before exchanging the
single-use external code. A timeout/uncertain exchange leaves the flow spent;
start a new explicit authorization rather than blindly replay the code. App
installation uses its own one-use state purpose and verifies the resulting
installation through the current App user token. Its callback lists available
repositories but creates no binding. Callback redirects only to the configured
same-origin project settings; there is no supplied return URL.

## Accepted review corrections before runtime

Private provider facts remain in separately gated GitHub projections. This first
slice does not change native work stages, blockers, discussions, notifications,
ordinary project events or exports from provider facts. A native stage itself can
reveal private repository activity. Standing automation therefore stays disabled
until either a separately reviewed explicit publication policy or a conservative
all-recipient current repository-access gate is implemented. Enabling an ordinary
rule must not silently expand the audience. The first slice can store a disclosed
rule and calculate its privately gated candidate state; this is not task movement.
The #153 outbox similarly stays undelivered until current recipient/subscription
repository and Flux authorization is enforced. No generic project event contains
private PR IDs/head/title/checks; no provider text becomes a native blocker.

Credentials bind configured App client identity, App numeric ID and verified
GitHub user ID. Installation listing must return that exact App ID. Stable IDs
are positive lossless decimal strings parsed from positive safe JSON integers;
unsafe rounded JSON numbers fail closed. Fetch origins and constructed path
segments are fixed and encoded; redirects fail, bodies are bounded, errors never
include private provider response bodies. Raw inbox payloads are internal only,
retained at most seven days after all per-binding processing is complete. A
supported header event must match its expected body shape and signed repo,
installation/object IDs; installation and user revocations only stop authority.
Cached/history reads require current repository proof as well as current Flux
access. Credential refresh is fenced by pending/uncertain state and cannot blindly
replay after a lost response. The regressions include a Flux-only project member
who receives no private GitHub facts through work, exports/events or the bridge.

## Recovery implementation refinement, 2026-10-01

Automatic gap recovery schedules only active bindings with existing verified
task/PR links, in 30-minute windows and batches of at most five. A durable local
reconciliation targets exactly its selected binding; neither a manager request
nor the scheduler fans out private Flux context to other same-repository bindings.
Only one pending local reconciliation exists per binding. Provider GET and retry
still recheck the binding author's current Flux, App identity, generation and
repository access. Scheduling bookkeeping never wakes an agent or changes work.

After a database restore and exact migration, the operator restore path always
revokes GitHub credentials/bindings and pending OAuth flows before starting API
or worker. Retain original source/link facts as unavailable history, terminate
old processing and require fresh explicit authorization and binding selection.
This GitHub safety step is independent of the optional agent-revocation flag;
agent restore policy itself remains unchanged. Complete portable export/import
of source history remains pending, with no credential or active grant export.

## Current-client correction and reader journey, 2026-10-01

Independent runtime inspection found that comparing App ID alone did not bind
stored credentials to the configured OAuth client identity. Before further
runtime, credential AEAD associated data must include the fixed provider host,
configured App and OAuth client IDs, Flux user, verified GitHub user and
authorization generation. The capabilities state must verify this envelope before
reporting connected; a changed configuration must refuse token use before an
outbound request. Pending PKCE envelopes also bind the App/client identity,
session and project, and fail before exchanging a code if configuration changes.
Old envelopes remain fail-closed and require an explicit fresh authorization;
they are not silently resealed or reused. Refresh generation/state fences remain.

A project viewer with their own currently verified repository access can choose
an existing task and read its original PR facts in the same settings route.
Viewing is separate from repository management and link mutation. Only native
task writers see the linking form; the manager Details entry remains management
gated. A Flux-only viewer receives no private names, links or counts. Browser
coverage must exercise the transition from unverified viewer to independently
authorized read-only viewer and clearing after current access loss.

## Credential/binding lock correction, 2026-10-01

Independent concurrent SQL evaluation reproduced a credential/binding lock cycle
and rollback poisoning at the previous runtime. Production provider instances
must be scoped to one outer GitHub transaction. Complete any durable preflight
refresh before a binding lock, then acquire a credential-row share lock in that
outer transaction and recheck current host/App/client/user/generation/state.
The pinned token capability is private to that transaction; every later identity,
repository and pull fetch reuses it without a separate credential transaction.
Only then lock and revalidate the binding and its processing row. Revocation
keeps credential-before-binding order. A changed preflight generation or revoked
credential fails closed; never carry the old token into the binding effect.

GitHub transactions use server-side lock and statement cancellation before the
unchanged 2-second driver query timeout. A slow external fetch must not leave a
revocation connection idle in transaction after a client-only timeout. Contention
may fail truthfully and be retried; it cannot acknowledge successful revocation.
Regression checks cover short read/revoke serialization, adverse transport
timing, signed authorization revocation, rollback drainage, current credentials
and subsequent pool/revocation usability. No publication authority is added.
