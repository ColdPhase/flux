Reviewer: root agent, not the #74 implementation author. Reviewed the proposed isolated-worktree design and current issue74 AC1–AC5/CO-3/CW-4. Accepted choices: distinct Flux login/App-user authorization/installation/binding; live per-reader App+user repository intersection; state/session/project+PKCE; immutable repository and PR identity; raw HMAC admission into a durable deduplicated inbox; current GET reconciliation; one binding failing independently; versioned disclosed native-task policies preserving manual edits and all required outputs; no merge/green-only completion; explicitly pending153 bridge and real external acceptance. GitHub's current App-user documentation confirms S256 PKCE and the user/App intersection; this is a documented vendor contract, not an observed installation.

Conditions to resolve before corresponding runtime effects:

1. CO-3 says private repository facts are not broadened implicitly to Flux project members. A private PR title/body/head/check/error copied into a native task blocker, discussion, notification, export or ordinary event bypasses the separate GitHub reader check. Define the derived native-stage publication rule explicitly. Conservative first implementation may keep private facts in a separately authorized projection and suspend automatic native-task effects unless every admitted recipient has the required currently verified repository access. Any broader publication policy must be independently recorded under CO-3's separately reviewed sharing rule; an ambiguous standing-rule click cannot silently broaden private source audiences. Add a Flux-only member regression against ordinary work reads, exports, event streams, notifications and153 inboxes.
2. Bind credentials and installation responses to the configured GitHub App ID and verified GitHub user ID. A selected installation redirect ID or guessed repository path is never proof. Validate positive safe integer IDs or lossless decimal strings; do not silently round large provider IDs. Callback state/PKCE one-use consumption, identity checks and encrypted credential replacement must be atomic under current session/project policy.
3. Current repository permission must gate cached facts and retained history too. Provider unavailability can expose only truthful non-sensitive unavailable state to an unverified reader; a formerly cached private title is still a private fact. Raw webhook payloads need internal-only persistence, bounded retention and no error-log echo.
4. Refresh rotates under a credential row lock, with an explicit uncertain state on a lost provider response. Do not automatically replay the consumed external refresh token. Outbound provider fetches have fixed HTTPS origins, bounded time/body/retry budgets, encoded paths and controlled redirects; payload URLs are navigation only, never server-fetch authority.
5. HMAC covers exact body bytes, not the event headers. Validate supported event/action/body identity consistently and reconcile already known objects before granting meaning to captured metadata. Revocation events may stop authority, never confer it. Background processing must recheck current rule-author Flux and repository rights before each effect/retry;153 consumption needs its own current authorized recipient/subscription gate.
6. Derived automation records must retain the rule/provider causal identity and disclose automation, while the standing-rule author remains the recorded authorizing human. Do not fabricate a human message or imply an eligible external review from a local receipt.

Auth/binding/link/inbox implementation can proceed once these safeguards are recorded. Native automation/publication and153 delivery must remain disabled where the corresponding condition is unresolved. This preserves the complete issue acceptance criteria rather than declaring the initial slice complete.
