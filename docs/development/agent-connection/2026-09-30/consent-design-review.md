## Verdict

Accept replacing the browser-session singleton with immutable request-bound choices, and accept request-local AsyncLocalStorage as a narrow server composition bridge for the pinned callback limitation. Do not implement the proposed sketch unchanged: canonical fields/continuation transitions, durable client binding and provider refresh-family behavior need the concrete contract below. The refresh-family collision is a material compatibility gap for two connections sharing one OAuth client ID; a new selection table cannot fix it.

Current `agent_oauth_selections` is indeed keyed only by session. `selectForOauth` checks the live owner session and live connection but accepts no signed OAuth request. `auth.ts` callbacks and consent-context therefore retrieve the same singleton. The connection/proposal public contracts and repository serializers hardcode Claude provenance. The proposed direction addresses these actual boundaries without changing existing project/grant/helper models.

## Canonical request and lifecycle

Keep signature verification and selection writes distinct from candidate lookup. Only a provider-signed, unexpired `oauth_query` plus a live signed-in owner/session can admit a selection. An unsigned initial authorize query can nominate a candidate fingerprint for lookup; it cannot write a selection, choose an author/connection from a header, or bypass provider client/redirect/PKCE validation. No missing-flow fallback to the legacy singleton is allowed.

The pinned signature canonicalization sorts every decoded `(key,value)` pair then encodes through URLSearchParams. The current Flux verifier matches this basic HMAC operation. Explicitly validate the signed query’s bounded length, exactly one signature and expiry, finite positive integer expiry, and ambiguous scalar parameters before projecting anything. Use the same verified parsed object for display, selection and bridge context; do not independently reconstruct fields from `get()` at several entry points.

The pinned provider’s exact transport/continuation fields are:

| Field | Observed behavior and treatment |
| --- | --- |
| `sig`, `exp` | Signature and query expiry. Verify on every signed ingress; exclude from stable grant fingerprint. |
| `ba_iat` | Millisecond issuance time, regenerated by `signParams` at each redirect. It affects fresh-login proof; validate/preserve for the provider, exclude from stable identity. |
| `ba_pl` | Provider-signed session ID proving post-login selection cleared before consent. Validate against the current session when present; preserve for provider continuation, exclude from grant fingerprint. |
| repeated `ba_param` | Provider-signed names manifest used to recover signed parameters from page URLs. Its list changes when continuation markers change. It is transport metadata, excluded from stable grant fingerprint; preserve multiplicity for verification/provider handling. |

Do not broadly ignore `ba_*` or arbitrary unknown parameters. The exclusions must be this documented, version-pinned list. Preserve unknown signed semantic fields in the fingerprint or explicitly reject them for the supported profile; the provider uses a passthrough schema, so a fixed short allowlist otherwise silently misses future grant inputs.

The proposed client/redirect/PKCE/state/scope/resource/nonce tuple is incomplete. Current provider authorization inputs also include **response_type**, **dpop_jkt**, **prompt**, **display**, **ui_locales**, **max_age**, **acr_values**, **login_hint**, **id_token_hint**, and **claims**, plus `request` / `request_uri` handling and passthrough extension fields. Sender-key binding, requested claims, login identity/authentication requirements and response behavior cannot be silently omitted. Reject duplicates for all scalar protocol/control fields, including signature/expiry/issuance/session markers. `resource` and `ba_param` are the known repeated forms; for this one-resource MCP service, enforce the exact configured MCP resource, not a vacuously true empty/every-equal check. Keep state, redirect URI, challenge and nonce values exact; avoid URL normalization or trimming that differs from provider interpretation. Distinguish absent from empty. Canonicalize the validated multimap with the pinned sorting rule and a versioned domain tag before hashing.

There are real semantic transitions, not just signature transport. `selected()` removes `prompt=select_account`; `created()` removes `create`; the sign-in after-hook removes `login` and satisfied `max_age`; consent removes `consent` and can reduce scopes/claims before internal reauthorization. The ALS store must retain the **verified incoming selection-flow fingerprint for the whole handler call**, even when the provider mutates `ctx.query` internally. Do not recalculate it from a modified internal query, and do not drop all prompt/authentication fields to make hashes match.

For a bounded implementation, make the supported profile explicit: today’s code grants Flux scopes plus optional offline access, not OIDC account/profile/email scopes or request objects/PAR. Validate/reject unsupported grant forms visibly. Establish selection identity at the first signed post-login request, after provider normalization/login transitions. Verify pinned transitions from that selected query through `/oauth2/continue` and `/oauth2/consent`; where a later HTTP redirect legitimately changes semantic fields, persist an explicit validated flow-alias/transition to the same immutable choice rather than matching by a reduced grant tuple. Scope/claims narrowing must retain the original selected identity and only reduce its ceiling. If broad OIDC/social/account-selection/PAR support is intended, prefer a server-owned random flow handle carried in provider-signed passthrough parameters and a durable transition record, with tested provider preservation; do not assert the callback-only fingerprint sketch already supports those modes.

The pinned `postLogin()` continuation itself does not make the body’s `postLogin: true` an authority proof: it calls authorize with postLogin cleared only when the signed `ba_pl` matches the live session. On the first continue after selection, `shouldRedirect` must discover the exact immutable selected flow and return false; then the provider generates the consent query with signed session clearance. Calling continue without a selection must fail or return to choice, never default. Capture this exact mechanics in tests.

## Request-local bridge

Create one AsyncLocalStorage instance in identity composition and pass it to both `createAuth` and `registerAuthBridge`. Each bridge invocation runs the awaited `auth.handler(Request)` under a fresh immutable store containing endpoint, verified-flow/candidate identity and parsed protocol facts. Do not use a module-level mutable “current connection,” mutate one shared store, trust incoming headers, or carry context into unrelated requests. Strip any proposed internal headers just as client IP forwarding copies are dropped today.

For JSON/form continuation and consent, read one bounded outer `oauth_query` value, rejecting ambiguous body/query copies before entering the provider; preserve the original body for provider processing. Continue uses the signed query, not the page’s cached selected connection ID. Server API invocations that could reach these callbacks without the bridge need the same explicit context wrapper or a visible missing-context failure. Routine `getSession` has no flow and must not invent one. Direct token/refresh calls must deliberately have no browser-selection context.

The provider callback receives user/session/scopes but not its query, as the checked-in excerpt correctly states. `shouldRedirect` does receive headers, but that is not a reason to smuggle trusted selection through a client-controlled header. Callback resolution rechecks `(owner, live session, selected flow, live connection, exact client, scopes/resource ceiling)` and returns the durable grant reference. Parallel requests for two flows must retain separate stores through awaits and nested provider reauthorization.

## Separate temporary selection from durable OAuth binding

Use a flow selection row with unique `(owner_user_id, session_id, fingerprint_version, flow_fingerprint)`, immutable connection ID, actual OAuth client ID, requested normalized protocol snapshot/digest, creation/expiry and any validated continuation aliases. Repeat exact choice is idempotent; another connection for that identity is a conflict. Do not let an expired signature regain authority merely because a row is retained. Bounded cleanup of expired flow rows is compatible with keeping token/proposal history.

Persist a separate durable grant binding naming owner, workspace, connection, agent and **actual OAuth client ID**, plus granted ceiling/version/provenance as necessary. Its ID is the new provider `consentReferenceId`. The reference partitions consents and survives in authorization-code, access/refresh-token records. `customAccessTokenClaims` resolves that provider-stored binding, rechecks live connection/agent/project/operation ceilings and emits exact connection/owner/binding claims. It must not read the browser flow table on refresh.

This separation makes expiry semantics precise: a signed browser query must be fresh at selection/consent; an authorization code has the provider’s bounded code lifetime and live-session validation; refresh has its own token lifetime and live grant checks. The claim callback has no original signed query, session or client argument, so promising a literal recheck of original signed-query expiry at every token issuance is unsupported without the binding/issuance integration. Decide whether completed-flow expiry also limits late code exchange; if so, retain and enforce that deadline through the durable binding/code path. Do not accidentally make a short browser setup expiry kill a valid long-lived refresh grant.

At MCP ingress, verify the provider-signed `client_id` against the durable binding’s actual client ID, `sub` against owner, exact resource audience and scope intersection before binding a runtime context. Session/connection/client/runtime session remain different identities. A clientInfo name, owner designation, or browser project change can never retarget the binding.

Existing reference IDs identify connections directly. Preserve those old tokens via an explicit legacy-reference resolver, without treating old browser selection rows as authority for new grants. Distinguish binding and legacy reference formats or guarantee an unambiguous namespace. Existing provider token/client checks still apply. No backfill should guess an original OAuth client from an owner label or a historical Claude proposal.

## Material refresh isolation gap

Confirmed in pinned source: `handleRefreshTokenGrant` validates client ID, scopes/resource reduction, then uses `refreshToken.referenceId` for new issuance. That supports connection isolation for ordinary valid refresh when Flux’s callback uses the stored reference.

However, reuse of a rotated token outside the replay interval calls `invalidateRefreshFamily(ctx, client_id, refreshToken.userId)`. That function selects/deletes **all refresh-token rows for that client+owner**, and deletes associated opaque access-token rows. It does not scope by referenceId, authorizationCodeId, session, or connection. The default replay interval is zero. Consequently, a duplicate/old token retry on Hubert’s first connection can destroy Hubert’s second connection’s refresh credentials when the clients share the same client ID. Increasing the replay window postpones this collateral boundary rather than fixing it. Also, successful cached rotation replay returns directly without `customAccessTokenClaims`; current connection revocation must be checked before that response path if claiming current authorization on every replay/issuance.

Resolve this before claiming independent reconnect/revoke/refresh. Preferred choices are a reviewed pinned provider fix/update or supported grant extension that scopes reuse invalidation to the stable authorization lineage/binding and performs current authorization for cached replay. Preserve PKCE/client validation, rotation atomicity, replay detection, token storage and fail-closed behavior. Keep this change in a narrow adapter/provider integration, not a parallel OAuth implementation in core. A preflight that merely declines a revoked token does not repair valid token reuse collateral, and swallowing provider errors does not restore the deleted second family.

Alternatively, distinct actual OAuth client IDs per connection can avoid this particular owner+client collision, **only if demonstrated with the real supported clients**. Several connections of one client type are explicitly required; a shared CIMD client ID or client-reused registration is plausible. Do not impose an unproved distinct-ID requirement, fabricate registrations, or lower acceptance to one connection per client. This provider dependency is a concrete unresolved blocker to full isolation, not permission to claim tests over synthetic different IDs satisfy the contract.

## Current authorization/provenance details

The live connection resolver checks owner, active owned agent, selected projects and central agent ACL under locks; policy includes the owner boundary. Keep that path. Selection/consent display must use current successful resolution, then select only its exact project IDs; current names are not an authorization shortcut. Sort selected-project access locks consistently. Effect/replay checks for standing actions must use the #152 core-owned authorization port inside the effect transaction; an OAuth callback’s transaction ending earlier cannot fence later effects against revocation.

New names/designations are bounded plain text. Add truthful generic external-client compute provenance for new connections/proposals and persist it when the proposal is created; preserve historical `user_operated_claude_code` provenance unchanged. Store actual OAuth client ID separately from the user’s designation and negotiated clientInfo/version. None proves which model ran, that instructions loaded, or which subscription paid. Update hardcoded UI/help/token/proposal serializers together without turning guessed metadata into a permission. F-018 activation/Start/Resume remains a separate tested integration.

Current `auth.ts` uses `loginPage: '/login'`, while the reviewed browser router has `/sign-in`/`/sign-up` and no `/login` continuation route. The current OAuth test starts already signed in and therefore does not verify this boundary. Supply/test an actual signed-out login continuation path, preserving the signed request and session change, rather than assuming normal app sign-in carries provider state. Forced login, expired-session choice and account changes must invalidate/rebind the selected flow truthfully.
