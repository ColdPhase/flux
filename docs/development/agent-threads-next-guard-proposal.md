## Ready next implementation boundary

Implement the server's task-thread turn budget and authoritative reset integration before exposing the new public writer. Preserve current OAuth/runtime/owner/project/source/grant checks, native command receipts and the complete shared task-use/Undo fence. Human threads and old contract-1 people replies keep their current behavior. No new MCP registration, review-class grant widening, public legacy-reply rejection or instruction cutover is included in this boundary.

The counter belongs to the actual task's unique agents thread, across all agents, connections and owners. One committed new agent message consumes one turn; the sixth is refused with `AGENT_THREAD_TURN_LIMIT`. A replay consumes no turn and returns the original effect only under current authority. Edits, deletion or conversation/author reassignment cannot recycle a spent turn or create a human reset. Message, counter, usage latch, native receipt/quota and quiet event commit or roll back together. Authorization or source failure cannot create a thread or consume/reset its budget.

Resets come only from a committed human message in that task thread, a committed new canonical artifact version belonging to that task, or a real canonical request state transition belonging to that task. Each durable boundary is consumed once: replay of an older human send, artifact version or request transition cannot reset a later exhausted budget. The adapters derive task/project from persisted rows. They do not accept a caller's `reset`, claimed artifact/version, task/project override or request-state declaration. Preserve existing #153 lineage/request budgets. Delivery ACK, polling, heartbeat, lease renewal, same-state metadata/version updates and a read-time effective-state projection do not reset. Private/helper/DM/recipient-only content is never copied into a shared transcript; a budget signal is not permission to disclose its source.

Use existing `taskUseRows`/retained sorted fences before the guard's task-local state. Add reset hooks at the actual canonical transactions rather than a second artifact/request store or post-commit event consumer that can miss/interleave a reset. Never reacquire upstream locks after holding a guard lock. The migration receives a new number only after a fresh live reservation audit; do not rewrite reserved 0082, 0048 or 0060. New-space agent routes remain closed until all accepted guard/reset cases pass. The SQL protection must continue to prevent unguarded agent insertion/conversation movement; ordinary generic endpoints must not acquire a caller-controlled bypass. A guarded internal native adapter may be tested under the existing execute/plan conversation grant only after this exact boundary is accepted and its mandatory guard is installed; it grants no new public/native authority.

## Concrete public/instruction seams that remain unresolved

Observed source, not runtime acceptance:

- `app/apps/server/src/agent-connection/conversation-actions.ts` exposes old `flux_reply_in_conversation` with operation `conversation.reply`, execute/plan classes and a conversation ID. `execution.ts`, `grants.ts` and core normalization use that same ID for grant scope, receipt fingerprint and message post-state containment. A lazy task-thread post cannot change its command target from null/task to newly created conversation on retry. Proposed future new-tool target: server-sealed task-stable resolution with the actual task's project, permitting a project-wide grant or a grant for that exact already-bound agents conversation; never promote a people-conversation grant or another task's grant. This target mode must be accepted and checked independently before public implementation. Review-class writing needs an explicitly accepted native operation/class or the canonical #153 response publisher; the existing v1 grant is not widened implicitly.
- `app/packages/contracts/src/cowork.ts` provides help/review/fix/handoff requests addressed to connections; it has no human-question kind/recipient. `flux_ask_question` is not registered. #153's internal `coWorkRequestInTransaction`/response adapters provide real canonical task/source/lineage fences, while public admission/inbox/resolving publication remain explicitly unavailable. A human question must use an agreed durable backing adapter and Needs-you path; punctuation or an unexposed peer-request record is not that capability.
- The old people-write allowlist includes result, proposed decision, human question and reply to a person who addressed that agent. Current plain conversation messages do not provide an authoritative addressed-agent/reply-cause record. Text heuristics must not create that exception or silently remove it. The peer must identify or accept its canonical causal record before the final old-reply refusal.
- `app/packages/core/src/agent-connection/playbook.ts` already ships `flux.cowork` **1.4.0**, tool contract 1. The #400 wording requested 1.4.0 before that existing bundle changed. Recommended clarification is a new immutable **1.5.0** instruction bundle once the actual post/get/question capabilities exist, with task-thread sequence/resume, one message per meaningful step and refusal recovery. Keep the original instructional outcome and supported Codex/Claude Code loading evidence; ACK alone does not prove delivery. #160's external branch is preserved.
- O-010 permits additive new tools under EXT-1 v1, but this alone cannot authorize new `AGENT_THREAD_REQUIRED` refusals on existing valid v1 people replies. Recommended final cutover is explicit EXT-1 **version 2**, preserving the v1 snapshot and recording the changed old-tool semantics, tool classes/error contract and instruction compatibility; any retained v1 route must retain its valid old behavior. A pre-release v1 replacement is an alternative only if @Zamojski5 explicitly accepts that narrower transition. Until that choice is accepted and every allowlist exception is backed, v1 remains unchanged. EXT-2 stays format 1/additive.
