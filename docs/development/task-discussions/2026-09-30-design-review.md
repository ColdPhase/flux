# Independent design assessment — Flux #154

Date: 2026-09-30. Reviewed checkout: `/home/hubert/Develop/flux/.worktrees/154-task-discussions`, head `f89ba1882a76b521b8228dad565050ee5629ff47`. Reviewed task body: `/tmp/flux-issue-154.json`. This is independent design feedback, not a production test or eligible GitHub approval. No implementation or GitHub records were changed.

## Recommendation

Accept the central direction: keep canonical `project_conversations` / `project_messages` and their existing flat per-conversation sequence; persist a separate compact creation notice in the task-creation transaction; create and bind exactly one task discussion only when a real public contribution commits. Do not add a synthetic human root, a parallel task-message store, general message parent/child nesting, or inferred historical bindings.

The proposed direction is the least disruptive architecture, but it is not yet a complete implementation plan. Actor-aware messages, real attachment storage, durable cross-entry-point command identity, contribution hooks in blocker/result commands, notice presentation, rollback semantics, and #136/#152/#153 interfaces must be explicit. Those are requirements of the accepted ACs, not optional polish.

Use the current project audience and core policy unchanged. Task discussion is a canonical conversation within that project. A source conversation is provenance; creating work from a message must not adopt that entire conversation as the task discussion or copy/reparent its opening message.

## What the code actually supports

- `packages/core/src/work/service.ts:createWork` inserts a work row, many-to-many links, and `project.work_created.v1`. It does not create a public task notice, root, or discussion binding. `createResult` inserts one canonical result and links; `updateWork` updates blocker/status. Neither writes a discussion contribution.
- `packages/core/src/work/ports.ts` already supplies a clean transaction/authorization boundary. `apps/server/src/work/adapters.ts` composes repositories and policy per transaction. Extend this pattern; do not add SQL imports to core or grow the architecture allowlist.
- `apps/server/src/conversation/store.ts` implements the current canonical message transaction, per-author retry key, source validation, and atomic sequence allocation. Creation and send explicitly call `human(principal)`. Migration 0006 has `auth_users` FKs for both conversation creator and message author and rejects empty bodies. Messages have no files, work identity, result identity, or discussion binding.
- `packages/core/src/conversation/commands.ts:normalizeMessage` requires nonempty text. Public contracts/routes likewise have no attachment-only command. A file-volume health probe and paired backup procedure exist, but no upload/authorization/attachment service was found. `docs/operations/export.md` explicitly says uploaded files are future work.
- HTTP work idempotency is optional `Idempotency-Key` plumbing, retained for 24 hours. The core `createWork` command itself has no mutation ID. A direct helper/MCP call can create again; a retry after key expiry can create again. This must be resolved for AC-1/AC-4, with a documented retention/replay contract.
- `apps/server/src/agent-connection/mcp-tools.ts` currently offers contexts, material reads/listing and proposals. It has no task/message write tools. #152 owns that extension; #154 cannot claim existing real MCP task writes are verified.
- Committed embedded-helper answers are already project-visible, including `request.prompt`, through `answerView` / `listAnswers` in `packages/core/src/personal-runs/service.ts`; own in-flight run views are owner-scoped. Preserve these actual source audiences. Do not assume every helper prompt is private, and do not automatically turn any helper prompt/answer into a new public task message. Accepted helper-result publication currently calls the shared result use case as the accepting human; preserve this actor and result ID, with distinct permitted agent provenance.
- Actor-sensitive consumers need changes: export currently hardcodes conversation/message actors as human; helper context uses an inner join to `auth_users`; search migration 0014 indexes messages as human; notifications model message actors/involvement as user IDs. Adding agent rows without updating these paths would silently omit or misattribute content.

## Concrete model and commands

1. **Distinct durable notice.** Add a narrowly scoped task-notice repository/table (or an equally durable typed activity record), carrying workspace/project, notice ID, exact work ID, event kind `task.created`, trusted creator kind/ID, created time, and authorized source references. Enforce one creation notice per work. Keep the ordinary identifiers-only domain event for stream invalidation and existing assigned-work notification behavior. Do not put the notice into `project_messages`, make it a fake conversation, or store public content in the internal event log. The notice is displayed in the project Conversation surface through a typed projection; opening the task before any contribution shows an honest empty discussion.

   The source refs already held by the work links remain canonical. If exact-at-creation source identity is needed, pin it on the notice or retain those immutable source links; do not reconstruct it from mutable latest labels. Server authors/time are trusted, not supplied by the browser. A no-source creation uses the project feed, not a guessed conversation. Do not silently choose the first/last source among several.

2. **One explicit discussion binding.** A nullable `discussionConversationId` on the work row (or a `work_discussions` mapping with unique work ID) is sufficient. Composite FK `(workspace_id, project_id, conversation_id)` prevents crossing the audience boundary; uniqueness prevents a conversation from being accidentally adopted by multiple task discussions. The root is its first canonical message, `sequence = 1`; no second copied root record is needed. Return `conversationId` and exact `rootMessageId` in an authorized discussion projection so every view opens the same identities, even when a paged newest window excludes the root.

   Legacy work has no binding on this checkout. Existing source links are many-to-many and are not evidence of a discussion binding. Leave these rows unbound until a new actual contribution; preserve all old source conversations/messages/links byte-for-byte. If an importer or another accepted branch possesses an explicit legacy binding, retain it exactly rather than infer one from title, body, date or source order. A legacy placeholder with replies stays historical, never overwritten or deleted.

3. **Shared contribution use case.** Add a small core use case with ports, e.g. `contributeToWork(principal, workId, normalizedCommand)`, composed inside the same unit of work used by blocker/result/public handoff changes. Its inputs identify the target task, stable client command/message UUID, actual body, authorized staged attachment IDs and optional typed canonical result reference. It accepts no client author/date and no arbitrary conversation retargeting. New browser/API/helper/MCP adapters all call this use case; generic conversation sends to a bound conversation go through the same append primitive.

   Under one transaction: lock current access/grant rows; lock command identity; lock the work row; reject reverted work; resolve and lock the existing bound conversation or create it; validate sources/files/result references; allocate the canonical sequence; write the message and relationships; set the binding when first; perform associated blocker/result effects; record stream events last. Multiple-task effects lock task IDs in sorted order. Maintain one lock ordering across direct contribution, generic reply, blocker, result and undo paths to avoid inverse-order deadlocks.

   Two simultaneous first sends must serialize on the work row. The winner creates the conversation/root; the second re-reads the binding and appends sequence 2. Both retain their own real actor, content and time. This is a database transaction test, not a UI race workaround.

4. **Genuine contributions and canonical results.** An explicit nonempty blocker save is a contribution authored by its saver, atomically with the task change and optimistic version check. Mere status/owner changes and blocker clearing need not become comments; document this boundary. A result publication writes one result object and a discussion message referring to its exact ID, in the same transaction. Keep its existing creator and links; do not manufacture an independent result copy in each view. If a result is about several tasks, deterministic per-task messages can reference that same result ID, with sorted work locking and retry identities. A public user handoff instruction is an authored contribution, while acknowledgments, heartbeats, execution logs and private helper interactions are not. #153 should consume this primitive for its targeted handoff, never create another chat or convert a received peer trigger into new authority.

5. **Real human and agent actors.** Prefer additive nullable agent-author columns alongside existing human author/creator columns, with an exactly-one-actor check and workspace-scoped agent FK. Keep every existing human value/time unchanged. Relax human columns only for newly stored agent rows; never insert an agent owner's human ID or a fake `auth_users` record as the speaker. Add an actor discriminant to wire projections and fix callers that assume `authorId` means a person. Actor ID/kind is canonical; connection/client/owner labels are trusted provenance, not identity supplied in message input. This also requires agent-aware retry uniqueness, search indexing, export actor collection, helper context reads, notification names/involvement and UI rendering.

6. **Attachment-only is real scope.** There is no service to reuse. A minimal file capability is necessary within this issue or as an explicit linked dependency; it cannot be replaced by a URL label or filename-only fixture. Stage bounded file bytes privately for the uploader in the existing files volume, with an immutable server-selected object ID/path, size/digest and ready state. The publish transaction validates uploader, current target project, ready bytes, all refs and current rights, then records the message/file associations. Empty text is valid only when at least one valid attachment is committed. Preserve pending files on save failure; abandoned staged files may be cleaned later. Database rollback need not erase private staged bytes, but it must leave no public attachment, partial root or notification. Every preview/download must reauthorize through the same policy. Stage bytes before committing references so a post-commit rename does not leave broken public files. Do not trust paths/MIME/name supplied by the client. Document limits and backup/export behavior.

7. **Durable retries.** Make new task creation and contributions carry a stable domain command UUID plus canonical fingerprint, reused by every adapter and covered by a DB uniqueness constraint scoped to principal, project and command. Persist identity with the created row/command receipt, rather than relying solely on the HTTP response cache. A changed payload with the same identity fails as a conflict. Replays recheck current read rights before returning data; MCP/helper must also validate the live connection/operation grant before executing or replaying. An old permitted command must not grant new authority. Existing 24-hour HTTP response handling may remain as transport optimization. Decide the no-key compatibility behavior explicitly; if it remains supported, it creates task + notice atomically but cannot promise deduplication of indistinguishable retries.

## Safe unused AI-task undo

Use a retained task tombstone / creation-reverted marker and an append-only `task.creation_reverted` notice, not deletion. Keep the original creation notice and exact historical ID; its link opens truthful read-only reverted history or is deliberately rendered as historical text. Exclude reverted tasks from active lists while preserving identity and source history. This is a lifecycle marker, not a new board status.

Require current project write authority, trusted AI-origin provenance, explicit owner/creator authority, expected current version and evidence the task is unused. Check the same locked work row as contribution writes. Refuse undo after any discussion contribution, result, later ownership/status change, decision/dependency/live handoff or other persisted use; a version-only check is insufficient if a related write does not bump that version. Retain the receipt so retrying creation cannot resurrect the reverted task. Race tests must show that either undo wins and the contribution is rejected, or the contribution wins and undo is rejected. Update notification fact reads so a delayed creation event cannot deliver a fresh assignment for reverted work; previously delivered history must resolve truthfully.

Preserve the upgraded data and use a tested paired DB/files backup plus matching image for operational rollback, with an explicit boundary for post-upgrade writes. If acceptance requires lossless downgrade after new-feature writes, implement/test a compatibility-preserving reversal rather than claiming backup rollback meets it. Share one draft key scoped to current principal + project + exact work ID across views, retaining body/files/references/client command UUID through pane changes and failures.
