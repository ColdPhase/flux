## Recommendation

Accept the proposed nullable legacy human field plus explicit agent actor as the bounded public-wire path. Preserve historical human JSON exactly; make new agent identity explicit and impossible to confuse with a human account. Internally, use a mandatory `{ kind: 'human' | 'agent', id: string }` identity in core ports and reader facts. Do not make core reason about nullable human columns or an optional wire escape hatch.

Define two valid variants, rather than a permissive interface that permits null without an actor or simultaneous human and agent identities:

```ts
type MessageIdentity =
  | { authorId: string; author?: never }
  | { authorId: null; author: { kind: 'agent'; id: string } };

type ConversationIdentity =
  | { createdBy: string; createdByActor?: never }
  | { createdBy: null; createdByActor: { kind: 'agent'; id: string } };
```

Compose these with the existing common fields. Apply the creator variant to **both `Conversation` and `ConversationSummary`**; listConversations currently projects the creator too. TaskDiscussion’s explicit root and messages naturally use the same message variant. Human serializers omit the additional field entirely, including new human replies in agent-started conversations. Agent serializers always include their explicit actor and null human field. No empty string, owner user ID, synthetic user or `agent:<uuid>` value goes in `authorId`/`createdBy`.

A mandatory public actor discriminant on every row is more uniform but changes all existing human payloads and forces an unnecessary wider client migration. It is a reasonable future versioned API, not needed for this bounded compatible slice. Opaque strings preserve a superficially nonnullable type but feed agents into human lookups, DM links, participation and retry namespaces; they require an implicit parsing convention throughout the application and are the least safe choice.

Preserving human JSON does not prove old clients understand new agent rows. Coordinate the actor-aware browser/server rollout before enabling writes and state this compatibility boundary. Do not claim arbitrary cached old browser assets or third-party clients are agent-safe merely because existing human fixtures stay unchanged. If continued old-client support for mixed conversations is a required public promise, record version/capability handling explicitly; dropping agent messages or fabricating human authors is not a valid compatibility solution.

## Storage and durable command identity

Add nullable `created_by_agent_id` / `author_agent_id` UUID columns, drop NOT NULL only from the existing conversation/message human fields, retain their human FKs, and enforce exactly one nonnull actor in each row. Use composite `(workspace_id, agent_id)` FKs to `agents(workspace_id, id)`; a UUID-only FK does not express the audience/workspace invariant. Preserve every historical human ID, message/body/source, timestamp, sequence, client ID and fingerprint. No guessed backfill or rewrite is needed: all existing rows have the required human column and null new agent column.

Keep the existing `(project_id, author_id, client_message_id)` human uniqueness. Add an agent uniqueness constraint/index on `(project_id, author_agent_id, client_message_id)` for nonnull agent authors. SQL null semantics mean the old unique constraint does not deduplicate agents. Use the same durable identity in lookup and lock acquisition: `(projectId, actor.kind, actor.id, commandId)`. Both ordinary conversation sends and task sends share that namespace and the append primitive. Include kind even if human and agent IDs normally differ; string equality is not an actor boundary. Preserve the task/operation fingerprint check so the same command cannot be reused for another task, operation or conversation.

Change `TaskDiscussionRepository.lockCommand`, `existingMessage`, `createConversation` and `append` to take a core actor reference. Replace `DiscussionMessage extends Omit<ConversationMessage, ...>` with a core record carrying a mandatory actor; blindly applying `Omit` to a wire union can lose its correlation and leaves domain state coupled to transport. DB adapters map split columns to that actor and reject impossible rows. Use focused pure actor/wire mapping so task reads, ordinary conversation reads, list summaries and retry returns cannot disagree about the same persisted identity. Core remains behind ports; SQL and schema stay in `packages/db`, server/worker compose adapters, and architecture allowlist grows by zero entries.

Use restrictive historical author/creator FKs, not `ON DELETE CASCADE` or `SET NULL` for these references. Revocation stops new writes but retains past authorship. Note the existing `agents.owner_user_id` FK cascades when deleting a human account: new restrictive references can make deletion of an owner with authored agent history fail. Document/test this real lifecycle implication; do not silently solve it by deleting messages. Existing human conversation/message FKs already retain historic authors. A future account-erasure policy must separately reconcile that history contract.

Use a new forward migration after 0033, reserving 0034 or the next actually free number with active owners; do not edit already implemented 0033 or older migrations. Replace the message search trigger in that migration. Current history needs no content reindex or author backfill because all current messages are human. New schema plus new browser/readers must be deployed before writers. Keep #118 exact ledger behavior and the accepted #58 0026–0032 merge-order checks. A downgrade must refuse after agent-authored rows exist instead of dropping agent identity or coercing it into a person; pre-use reversal must restore the old constraints/functions exactly.

## Authorization and authorship

Derive actor exclusively from the authenticated principal after current central project-write authorization. Reject `fixture` and unknown kinds; never accept an author, owner substitution, creator or timestamp from command input. The first agent contribution records the same real agent as conversation creator and sequence-1 author. Human follow-ups remain human, even when they accept agent suggestions. Existing helper result acceptance remains attributed to the accepting person, with agent provenance distinct; reading or generating a helper answer never creates a discussion message.

The current session HTTP route remains human authenticated. Removing the core’s human-only guard enables a trusted core caller; it does not authorize arbitrary HTTP callers to nominate an agent. #152 still owns live MCP task/message scopes and entry points. Existing `flux.proposal.write` is not discussion-publication authority. MCP/helper replay must revalidate its current connection, selected project and operation grant as well as current project access before returning a receipt; a bare remembered agent principal is insufficient evidence of a live connection grant. Tests of direct core agent contributions demonstrate actor storage, not real-client authorization acceptance. #153 generation/claim fencing remains required for its public handoff path.

Historical reads authorize the reader for the project, not the old author for present access. A revoked agent’s earlier messages must remain readable to current project readers and retain agent identity. Name resolution may use an authorized current project directory or a truthful agent fallback; the actor ID remains exact even when no current display name is available. Never replace a missing/revoked agent with the owner’s name. Render a clear agent marker even when an agent chooses the same display name as a person.

ID-only readers such as live message-source authorization, work source validation and inline create-work actions do not need new author policy merely because the source is an agent message; they retain their current exact-project authorization. Inspect their types/build, but avoid expanding scope by changing unrelated object behavior.
