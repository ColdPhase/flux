**Accepted for bounded implementation as written.** No necessary design correction blocks proceeding. The explicit FIRST current authenticated authority → one command identity → ordered domain locks/writes → one final audience batch is consistent with the previously accepted deferred-event boundary. The shared collector supplies composition, not authorization or a second command ledger.

The problem is concrete in the pinned source: `apps/server/src/work/adapters.ts` records native events inline; `apps/server/src/personal-runs/adapters.ts` uses `workUseCases(tx as Database)` to record a result inside proposal acceptance. `packages/core/src/personal-runs/proposals.ts` then updates the proposal, records its decision and queries names to render the response. A nested savepoint shares rollback but leaves the stream serialization lock acquired before those later operations. Reusing the native result ports and a single collector within the already-open exported Transaction fixes that ordering without redefining ownership or storing duplicate content.

The implementation must preserve these already stated requirements:

- `nativeWorkInTransaction(tx)` prepares work/result and discussion operations against the same real transaction and one shared guarded collector. A composing caller uses this one session; it must not independently flush a discussion-only session in the same composition. Discussion-only compatibility remains useful for existing callers. Return no raw executor/pool and introduce no separately committing transaction or core SQL dependency.
- Guard every admitted asynchronous use case, including read-only actions. An active-command flush rejects before closing; the first admissible flush closes preparation, repeat flush returns the exact same promise, late calls fail, and a rejected flush stays rejected. Copy/snapshot nested intent data as well as trusted principal/scope/kind/canonical IDs; a mutable nested object cannot change the eventual event after preparation.
- Prepare every final-state audience before the FIRST event insert. Only events and their derived audience/outbox storage follow that point; native response hydration, proposal names, coordination/use-debit/receipt/outgoing writes and domain reads must already be complete. Reuse existing `recordEvents`; a loop around inline `recordEvent` is insufficient.
- The ordinary work/proposal UoW owns final flush and awaits it before commit. Proposal result and proposal decision events share the collector and the actual accepting human. Preserve existing optimistic versions, native ownership, command/retry semantics, notices, source links and private helper-output boundaries. This is not permission to publish personal provider output beyond the accepted proposal contract.
- Action/flush errors must propagate through the owning transaction; callers must not catch and commit partial domain work, flush after failure, or run a fire-and-forget/post-commit flush. A caller-owned composition remains responsible for this obligation. #152/#153 retain their real authority, connection/runtime/grant, one-ledger, generation/session/DB-time lease, quota/receipt/outgoing fences and sorted multi-task lock order; a test marker does not certify those systems.

Required fresh implementation evidence is appropriately scoped in the proposal. Use real PostgreSQL/HTTP work/decision/result and helper proposal acceptance. Prepare real native work plus a genuine agent contribution in a caller-owned transaction, establish canonical IDs and no stream lock before flush, then mutate actual final domain/audience state and flush once. Instrument the real executor to reject any domain/policy read or write after the first event insert; prove every audience prepared first. Verify lifecycle, immutable nested intents, replay/read-only empty intent batches, no nested commit, and rollback before and after actual flush across native work/result/notice links, discussion root/message/sequence/Search, events/outbox and the final marker. Cover a helper proposal acceptance rollback after the proposal decision as well as success so the former nested-result ordering cannot return unnoticed.
