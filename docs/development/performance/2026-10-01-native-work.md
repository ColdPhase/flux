## Dataset, method and proposed budgets

Create1000 actual native WorkItems through the existing public project work
commands in an isolated Docker project: two registered human contributors,
500 open/300 in-progress/150 blocked/50 finished, alternating real owners,
meaningful branch/sensor/privacy/testing outcomes,100 native message/material
source links, one current and one proposed decision, and linked results.
A pivot parks30 open objects without rewriting their original status. Count
exact actual objects through the native paginated API for both accounts, and
exercise a deep object's same native details/source route. These are human work
states, not fabricated agent execution. No direct SQL seeding, fake identity,
mock collection payloads or model dispatch. Record fixture setup independently
from measured UI operations; never reduce the dataset to make a target pass.

Docker VM observed14 CPUs/8,216,887,296 bytes, Engine29.1.2. Browser toolchain
is pinned Python Playwright1.62.0; record actual Chromium build. Compare1280×800
DPR1/zoom1 desktop and390×844 DPR1/zoom1 with explicit CDP4× browser CPU throttling.
The second profile is viewport/CPU emulation, not physical Android/iPhone/iPad.
API/PostgreSQL stay uncapped; other existing projects are not terminated. A
matched3840×2160 observation may record available context without claiming a
physical4K or a200-sample distribution.

All four numeric distributions have30 warm-up actions and at least200 measured
actions over at least60 seconds, per profile. Navigation uses fresh documents
with the same real dataset/session; it is not a fresh browser process/network
cache per sample and must be labelled accordingly. DOM event→paint measurements
use the browser's one monotonic clock, not Python/server wall-clock subtraction.
Report test-driver navigation time separately. Native trusted Playwright input
is observed by capture listeners and following animation frames; elapsed times
include the actual React/DOM work. Wheel actions must actually move the intended
list; boundary no-ops are not valid scroll samples. Record deadlines and missing
samples instead of interpreting timeout as a passing result.

Initial collection fetching must be bounded independently of total project size:
at most100 WorkItems per initial page and at most4 initial work/decision/result/
summary collection calls. Render at most200 work rows at first paint (and keep
later rendering bounded), including wide layouts. Those are optimization targets,
not permission to drop older objects or show incomplete counts as complete.
Record actual initial API request count, body/transfer bytes, fetched records,
current DOM element count, rendered work-row count and target JS heap/DOM counters
where supported. Label target heap versus driver/container RSS and sampled
maxima truthfully; unavailable memory counters stay unavailable.

Preserve all accessible native work via explicit pages/windowing/search or an
equally complete independently accepted design. Exact group/owner counts, native
object/version/status/park meaning, current audience, message attachment/source
and back routes must survive a fetch/render correction. The initial source loads
all lists through repeated100-record pages and renders all task rows; a baseline
may fail the bounds even if latency fits. Do not truncate it to the first page
and call the same state line/counts/message links complete. Any new public query,
summary/index or pagination contract needs independent design review before its
implementation; this kickoff does not accept such an API.
