# Flux package licensing proposal

**Status:** proposed under [O-002](application-architecture-proposal.md), 27 September 2026. The application architecture and this package boundary need independent acceptance before new packages are published. This document does not change the license of an existing file.

The repository currently has an [AGPL-3.0 license](../../LICENSE). Keep the Flux application in `apps/web`, `apps/server`, `apps/worker`, `packages/core`, `packages/db` and `packages/agent-runtime` under AGPL-3.0. Propose **Apache-2.0** for independently usable `packages/contracts`, `packages/sdk` and `examples/external-agent`, with each package's own license, SPDX metadata and notices. Their source must avoid imports from AGPL-only application modules so external developers can implement an agent in Python or another frontend against the documented HTTP API. No closed enterprise edition is proposed; possible paid services are hosting, deployments, migrations, maintenance and enterprise support, subject to a later business decision.

The [Apache Software Foundation's compatibility explanation](https://www.apache.org/licenses/GPL-compatibility) and the [GNU license list](https://www.gnu.org/licenses/license-list.html#apache2) support Apache-2.0 code being included in GPLv3-family works in that direction; they do not establish that AGPL application code may be copied into an Apache-only SDK. The first package PR must identify ownership of new files, add package-level license texts and notices, and check the dependency tree before distribution. Treat legal interpretation and third-party terms as a release review item. Keep the existing root license and product direction intact until the accepted package boundary is implemented.
