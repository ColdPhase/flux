### F-036 — simple AI: everything is an agent

The points of #851, with the later answers applied (point 11 comes from #868):

1. **One Flux is one company** (F-037). AI belongs to a person for the whole Flux. Each space
   has its own AI switch. Guests have no AI.
2. **Connect AI once per person.** A person may hold several connections at once: a Claude plan
   (the unmodified Claude Code), a ChatGPT plan (the official Codex) and an API key, including
   the Claude Max, Ultra and Team monthly API credits. The API-key providers are F-020's list:
   Anthropic, OpenAI, OpenRouter, Gemini or an OpenAI-compatible or self-hosted endpoint
   ([coordinator default C-11](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Removing a connection pauses the agents that use it ([coordinator default C-3](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
   Together the connections power all of the person's agents. Flux sets no limits of its own and
   shows the provider's remaining usage. An API key keeps one daily budget. When a plan hits its
   limit the agent pauses until the reset and never switches to another connection (#854, #843).
3. **Everything is an agent.** Each agent has a name, saved instructions, its own model from any
   of the person's connections, and a memory of only what its owner told it to remember, which
   the owner sees and edits. An item is added only by the owner's own message ("remember
   that …") or by editing the list; an agent never adds to its memory by itself. The first agent
   is **Assistant** and answers `/ai`. More can be added, such as Planner or Reviewer (#857).
4. **Talking to your agents.** Each agent is a private conversation in Messages, with Assistant
   pinned first. `/ai` works in every conversation and is answered privately; Show everyone
   posts the answer as "Ada's Assistant" (#842, #1232).
   - **What `/ai` may use.** Inside a conversation, only what that conversation's audience can
     see, so Show everyone never publishes anything private ([coordinator default C-12](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). In a private conversation
     with your own agent, the agent can use anything you can see. The agent's instructions and
     memory still go to the provider with a shared request ([coordinator default C-7](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)), but a shared answer never
     quotes or reveals them ([coordinator default C-8](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
   - **DMs between people.** AI is allowed there. Both people see one line, "Ada used AI here
     (Claude)", also when an agent opens a DM for its owner ([coordinator default C-2](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). No space switch governs
     DMs.
   - **Schedules** are made by telling an agent in plain words; they are listed and confirmed in
     its conversation and their results arrive there. The morning summary is one such schedule
     (#858), and the only one: the plain, non-AI summary of Notifications (#350) is removed.
5. **Tasks reach agents through their owner.** The owner gives a task to one of their agents in
   the Owner field. One setting: "When someone assigns a task to me: Do nothing / Give it to
   [agent]", with exactly one agent and "Do nothing" by default. Nobody prompts someone else's
   agent; messages from anyone but the owner are context (#856). The agent's owner or the space
   admin can **Stop** an agent working on a task, and the owner is told who stopped it. The
   admin's Stop also reaches a local client ([coordinator default C-6](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
6. **Agents work in the task's discussion.** They talk there with other people's agents when
   both owners are among the task's people, using only what all of them can see. The task's
   people are its creator, its owner and anyone who wrote in its thread ([coordinator default C-10](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)); a message
   written by an agent does not add its owner ([coordinator default C-5](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). A question from another agent never makes an
   agent change anything ([coordinator default C-13](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Each agent's owner pays for it, sees its answers live and can
   delete them. Subtasks for other people wait for the owner's OK, with Approve all. When it
   finishes, an agent follows its "What it may do": Done with Undo, or handed back for review
   (#856, #841). Only read also hands the task back ([coordinator default C-1](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). **Review is that row:** the
   formal co-work review verdict of F-016 and F-018 is removed as a coordinator default
   ([coordinator default C-9](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)), and a separate reviewer is optional, for example a subtask for a Reviewer agent.
7. **Approvals per agent.** Each agent has one row, "What it may do": Only read, Do it and tell
   me (the default) or Ask me first. Deletions and other people's things always wait. Undo sits
   on each agent message; there is no Activity list. The Inbox holds only what needs the person
   (approvals, tasks handed back, questions), one item per agent run with Approve all; reports
   go to the agent's private conversation, never to the Inbox (#855). **Only the owner
   approves:** approving, editing or skipping a waiting item, Approve all, and accepting a
   decision happen only in the owner's own signed-in session. No agent, server or local, has a
   tool for it, not even for its own waiting item (kept from F-027's owner-only Apply).
8. **Rights.** An agent has exactly its owner's current rights: no agent project grants and no
   manager requests (#855).
9. **Code.** Server agents work only inside Flux, read the connected GitHub repository and read
   the web, and never write to either. Code changes come from the person's local Claude Code or
   Codex over MCP: one sign-in, no scopes or switches, the same "What it may do" row, and "work
   on #4" from the editor (#859). Being the person's own tool, a local client may post in a space's
   conversations as the person, marked "via Claude Code" or "via Codex"; server agents never post
   there (Hubert, 2026-11-08, #1089).
10. **Notifications.** "Only what needs me" includes agents waiting for you, and Quiet hours is
    one row (#872).
11. **Blocked.** A task blocked on a person, a decision or another task returns to Doing by
    itself when that resolves; an agent owner resumes its work (#868).
12. **Capacity.** Flux works out how many agents run at once from the server's memory (about 2
    on 4 GB). The rest wait with "Waiting for room on the server". The operator can change the
    number in the config file; there is no setting in the app (Hubert, 2026-11-03, #860;
    [where agents run](ai-modes.md#rt-3--isolation-and-capacity)).

**What goes away:** Flux's own run limits and the seven reasons a change waits; agent project
grants and manager requests; MCP scopes, capability switches and standing grants; reactions and
background suggestions; the local waiter (#754, closed); drafts of messages to other people; the
space Agents tab; a separate "assistant" concept; the formal co-work review verdict on a pull
request head ([coordinator default C-9](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).

### F-037 — one Flux per company, with Spaces

From #874 and the people-and-spaces answers on #861:

- **Spaces.** One flat list of Spaces replaces projects. A space can be a department, a team or
  a project. There are no group headers and no workspace switching. "Project" becomes "Space"
  in every label; internal code names may stay.
- **One workspace per Flux.** Setup creates the company. No screen, API path or document shows
  more than one workspace, although the data model may keep its workspace table.
- **Joining.** With SSO, everyone the company's identity provider lets in joins on their first
  sign-in, with no invitation; IT controls access in the identity provider. Without SSO, the
  company admin invites people with links, as F-035 describes: the admin copies a one-time link and
  sends it themselves. Flux sends no invitation email.
- **Who sees a space.** Only the people added to it. The default space **Everyone** holds the
  whole company.
- **Space settings.** A name, its people ("Add people", chosen from the company) with two roles,
  member and space admin, and an AI switch. The creator is an admin and can make others admins.
  The company admin can change any space, except an encrypted one (below; its people stay with
  its own admins, [coordinator default C-4](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). A space admin
  can also leave the space, rename it and delete it; the company admin can delete any space, but not Everyone, which holds the whole
  company. There is no global AI switch.
- **Company admins and removed people** (Hubert, 2026-11-05). A company admin's sidebar and every list from the shell hold only the
  spaces they belong to, like everyone else's, and their search and Inbox do too
  ([coordinator default C-15](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Settings › Company holds
  the people, the company name, every space (an admin can add themselves to one, as its admin (a coordinator inference of #903), or delete it, and sees an encrypted space's name only)
  and the people who left or were removed, with **Restore**: they sign in through SSO as usual and join Everyone, and are added to other
  spaces by hand.
- **Creating a space** is one window: name, people, an AI switch (on by default) and an
  "Encrypted" switch (off by default; when on, it asks for an unlock password and offers the
  recovery code). A new space has no template and no goal and starts with Conversation, Tasks,
  Map and Wiki.
- **Encryption per space.** Chosen at creation and irreversible. An encrypted space never has
  AI. After a server restart it stays locked until a space admin enters their unlock password;
  members see "Locked, waiting for an admin", and the rest of the company works normally.

  delete the space but cannot read it unless a space admin adds them. The engineering option to

- **No data migration, and v0.1 is refused** (Hubert, 2026-11-09, [#1176](https://github.com/ColdPhase/flux/issues/1176)).
  Flux is pre-release with no installations to convert: v0.1 had no users, so v0.2 converts no data, backfills nothing
  (a v0.1 workspace is not made the company) and keeps no compatibility with it. `./flux upgrade` and the migrator refuse a
  database that v0.1 wrote, and `./flux restore` a v0.1 backup, with a plain message: install v0.2 fresh; there is no import
  (the project export has none). The [upgrade guide](../operations/upgrade.md#from-v01-install-v02-fresh) and the v0.2 release
  notes say so.

  server agents.

    tab at most 4 requests a minute; a navigation at most 8 requests, with no repeats, and

    content; an image of at most 250 MB; a restart in at most 5 s. The performance run gains a

    confirms it in the background. If that fails, the previous state returns with "Couldn't
    save · Try again".

    replacing the 15–20 s polling. After a reconnect Flux does one catch-up fetch.
- **By the standing UX rules:** one plain label per thing on every device, and AI words leave
  everyday screens.

MKV, AVI, WMV, FLV and every other video stay ordinary download-only files at the ordinary limit. **Flux never transcodes and has no ffmpeg.** A browser that cannot play the file (the player errors, or `canPlayType` is empty) shows "This browser can't play this video." with Download. **Seeking.** `GET /api/v1/files/:id/video` answers the file's own container type (`video/mp4`, `video/webm`, `video/quicktime`) as an attachment with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: private, no-store` and `Accept-Ranges: bytes`. A `Range: bytes=a-b` (also `a-` and `-n`) answers 206 with the exact `Content-Range` and `Content-Length`; a range past the end answers 416 with `Content-Range: bytes */size`; several ranges or a range that does not parse are answered with the whole file (200), which the standard allows, and `If-Range` is answered with the whole file because Flux sends no validator. The download route `GET /api/v1/files/:id` honours the same ranges (a resumed download) and keeps its type, `application/octet-stream`. A file up to 5 MiB (a small video too) is read whole and its SHA-256 verified on every read, as every file always was, and a range is cut from those verified bytes; a video over 5 MiB is read from disk as a stream, a chunk at a time, never into the API's memory, with its stored size checked, and its SHA-256 verified in the export bundle. **What is verified when (#1411).** Every file's SHA-256 is computed once, from the bytes as the upload arrives, and stored with its row and size. Sending a message reads no byte of its files inside its transaction: there it checks the rows (the sender's own, ready, unexpired, unsent, with a recorded digest) and that each object is on disk with exactly its recorded size, from the file system's metadata alone (`FileStorage.present`; a sealed object's 36 bytes of header and tag on top), and asks no other database connection. Just before that transaction opens, holding no connection while it reads, the send hashes each of the sender's files up to 5 MiB (at most 10, a sealed one opened by its tag) and refuses one whose bytes no longer match, so such a file changed on disk since its upload still cannot be sent (#154). Bytes changed later are caught where they are read: a file up to 5 MiB on every read (a sealed one by its tag as well), a video over 5 MiB by its size on every range and by its digest in the export bundle, which hashes it before it writes any header. A video over 5 MiB whose bytes were changed in place but kept their size can therefore be sent and played; only someone who can write the files volume can do that, and the export refuses it. Reason: hashing each whole video inside the transaction held one of an API process's 10 database connections per send for as long as the hash took, and 12 sends of 200 MiB videos at once took every connection and failed others' requests (audit of #1270). **Access is checked on every request, ranges included**, in the database: a person who lost the space (#592) gets 404 on the next range; a stream already on its way is not recalled. **Limits.** A video of a plain space is at most `FLUX_VIDEO_MAX_MIB` (default 200 MiB, 1 to 1024), an operator setting documented in the configuration reference, the requirements and the reverse-proxy page (its body limit must allow it); every other file stays at 5 MiB; the page reads the cap from `GET /api/v1/files/limits`. One message carries at most 10 files, its videos together at most that cap and its other files together at most 20 MiB. Waiting (staged, unsent) videos of a person in a space count apart from their other waiting files: up to one cap's worth of video besides the 100 MiB of the rest. A video is an ordinary stored file for storage: counted in the files volume, kept for the same 7 days while unsent, removed with its message or space. The upload is the raw body streamed through hashing into a scratch file (no whole-file buffer; the API holds one chunk), at most 20 minutes to arrive for a video (30 s for the rest), and fails cleanly: an upload that is cut, too large (413 from the declared length before any byte, or from the count while it arrives), not a video or timed out removes its scratch bytes and its reservation, and the sender's Retry upload sends it again under the same upload id. **There is no partial-offset resume**; the page's queue already retries. **Poster.** The sender's browser draws the video's frame at 0.1 s into a canvas (at most 640 px on its longest side, JPEG) while the file uploads, and sends it after the video is staged to `POST /api/v1/projects/:projectId/files/:fileId/poster` (raw bytes, at most 512 KiB, the video's uploader only, once the file is ready and unsent).    one-time image switch on upgrade passes #1241's upgrade matrix. No separate search engine.
2. **Embeddings: an optional local embedding container** (bge-m3 class), **off by default**, for operators with larger servers;
   hybrid ranking (reciprocal rank fusion) only while it is on. Nothing is embedded through a person's own connection.
3. **Summaries on demand only:** a tool that summarises a conversation or thread since a date, paid by the asking agent's
   owner. Nothing is stored.
4. **Scope and window:** an agent searches **every space it may read now**; the brief's window shrinks (for example to 20),
   and the answer-accuracy evaluation sets the final size.
5. **What is indexed:** what `flux_search_project` covers today (space messages, Wiki, tasks) **plus DM messages, which an agent
   finds only within a run in that DM**.
6. **People's search (⌘K) moves to the same BM25 ranking:** any word, Polish stemming, ranked.
7. **Answer accuracy** is measured with a real API key the founder provides (stored outside the repository, never logged),
   instead of strata.

Encrypted spaces are never indexed for AI or embedded (unchanged, [AG-10](assistant.md#ag-10--ai-in-a-space)).

**Founder answers after the accuracy run (Hubert, 2026-11-12, on #1242).** The brief's window is **20 messages**, not fewer
(#1291), although the search page alone answered as well with fewer tokens on the bench. The index keeps **Polish and English
stemming**, although Polish alone found a few more answers on the bench (recall@10 0.60 / 0.78 against 0.58 / 0.73, question as
asked / bilingual; [research](research/2026-11-ai-context-retrieval.md#answer-accuracy-on-claude-sonnet-55-2026-11-12)).

**Engineering choices (#1296).**

- **The database image** is built from [`docker/database/Dockerfile`](../../docker/database/Dockerfile): the official
  `postgres:18` on Debian 13 by digest, the `pg_search` package of a pinned ParadeDB release checked against its sha256, and
  `pgvector` at an exact version (`pg_search` requires it). `pg_search` is preloaded by the image's entrypoint whatever
  command the container is given. The release publishes it as `ghcr.io/coldphase/flux-database`, by digest, built, attested,
  scanned and signed with the application image; a source checkout builds it.
- **Same behaviour as the Alpine image.** v0.2.0's database (musl) compares text byte by byte under `en_US.utf8`. The new image
  builds `en_US.UTF-8` from glibc's C locale, so ordinary text indexes stay valid and `ORDER BY` gives the same order, and
  the `postgres` user keeps Alpine's id 70, so the data directory's owner does not change. No dump and restore is needed. Case
  mapping and character classes still differ for rare and recent Unicode characters (independent review of #1314), so migration
  0065 recomputes the stored search columns that differ and rebuilds every index built from an expression, a text-dependent
  predicate or a non-B-tree method ([upgrade](../operations/upgrade.md#v021-the-database-image-changes)).
- **One BM25 index over `search_documents`**, the table people's search already keeps current in the writer's transaction:
  title and body each indexed twice, with a Polish and an English stemmer and accents folded, plus the kind, audience, space,
  author and time as filter fields. Sealed rows (encrypted spaces) are placeholders without text and are left out of the index.
  It follows every insert, edit and delete in the same transaction: no job, no lag, no idle statements.
- **pg_search plans only Flux's BM25 statements.** Its custom scan, which scores BM25, refuses any other condition on a column the
  index holds twice ("Query is ambiguous"), so the image turns it off by default and each BM25 statement turns it on for its own
  transaction (`SET LOCAL paradedb.enable_custom_scan = on`); every other statement plans as before. Its planner notes are off too.
- **A run reaches its own place** (founder decision, Hubert, 2026-11-12, on [#1324](https://github.com/ColdPhase/flux/pull/1324): the #1242 wording "every space it may read" applies to private runs and local clients; #1290, C-12, C-37): `flux_search` and `flux_read_around` follow `runReaches`, so a run in a space searches that space (its answer may be
  shown to everyone who reads it), a run in a DM that DM, a private chat and the owner's local client every space the owner reaches
  ([AG-12](assistant.md#ag-12--finding-older-messages-f-042)).
- **Access is decided at query time,** never stored in the index: the statement receives the audiences the caller may read
  now (the access policy's `memberFilter` / `visibleFilter`, and for an agent the spaces with AI on), as people's search does
  today, and the index applies them before ranking and the limit. A grant lost, a space's AI turned off, a person who left, a
  removed, deleted or edited message: the very next query reflects it. Nor does what the caller may not read take part in the order: see
  the 2026-11-13 decision under the engineering choices of #1293.
- **Licences.** `pg_search` is AGPL-3.0-or-later, which Flux (AGPL-3.0-only) may ship; its source is the release tag the
  Dockerfile names. PostgreSQL and `pgvector` are under the PostgreSQL Licence, OpenBLAS (a `pg_search` dependency) BSD-3-Clause.

**Engineering choices (#1292, summaries).**

- **`flux_summarize` returns a digest and asks nothing of Flux's own models:** "by the calling agent's own model in its own run" is the
  only way both engines get it, since a local Claude Code or Codex has no model connection on the server. The tool reads the messages the
  caller may read now, in a range, and the agent writes the summary, paid as its run is (AG-11); no summary is stored, so there is no
  record to keep current, to hide or to bill.
- **An answer is a page:** about 16,000 characters (about 4,000 tokens, far inside an API-key run's 64,000), one line per message with a
  heading for each day and, in a space's main conversation, for each thread; a line break in a message is a visible mark, so a message
  cannot pass as another line. It says when it stopped early, how many messages remain and its `next` (the stored time with its
  microseconds and the message id), and the range is read in pages without a gap or a repeat.
- **Where it reads** is a space (its conversations, not a task's discussion, which is the task's), a conversation or thread, a task's
  discussion (through the task's own read, its people) and a run's direct message; the id is checked in the agent's own company, so
  another company's or an encrypted workspace's space is not found, and the reach rules of search apply (C-12, C-37).

**Engineering choices (#1293, people's search).**

- **Plain words** (⌘K, the search API, an agent's `flux_search`) are answered by the BM25 statement: any of the words, Polish and English
  stems, accents folded, ranked by rarity among the hits the caller may see with a word in a title counting double; the word being typed is also a prefix, and a title
  tolerates one typo in a word of four letters or more. Quotes, `or` and `-word` ask for exactly what they say and stay on the exact
  index (every word, no stems). The groups of the dialog, its keys and its one request per debounce are unchanged.
- **No statistic of the whole index may influence what a caller sees** (founder decision, Hubert, 2026-11-13, on the review of #1326, which
  found that hidden writes swapped two visible results; it applied to an agent's `flux_search` already on `main`). pg_search's score counts
  how rare a word is over every row of the index, restricted spaces, other people's direct messages and other workspaces included, so it is
  not used: pg_search only **matches** (constant-score clauses that say which word a hit holds and where, under the caller's audiences; the
  caller's other filters apply after the scan, since pg_search scores a filter on one value by its rarity in the whole index) and the
  order is BM25 computed in SQL over the visible hits: a word's document frequency, the number of documents and their average length are
  counted among them and nothing else; a document's own part comes from its own tsvector and nothing else: its length (`length(tsv)`)
  and how often each query word the index found in it occurs there, in the title and in the body (#1387, below). The same
  statement serves the people's search and the agents' `flux_search`; `search-hidden-ranking.test.ts` pins it with writes in a restricted
  space, another workspace and other people's direct messages, and with hidden documents that repeat the words at every length. An
  occurrence counts 2 in a title and 1 in a body (BM25F); a hit found only as the word being typed or with a typo counts half the query
  words' average rarity; at most twelve words are looked up. The cost is a few more scans for each search and no index-wide statistic.
- **Recall recovered inside that rule (#1387, coordinator call on the #1341 review, 2026-11-13).** Two causes of the drop to 0.467:
  1. **A defect:** pg_search keeps a constant score (`pdb.const`) only up to 2048, and #1326's constants for a scan's fourth and fifth
     words were larger, so every word after the third of a scan was read as the third, in the title. The constants are now 2^-12 to 2^10
     (a score is a 32-bit float, exact over 24 binary digits, and the audience filter adds exactly 1), still five words a scan.
  2. **Term frequency one and b 0.75:** a word's count now comes from the document's own tsvector (`ts_rank_cd` of a one-word query
     without normalisation is that count, the word as typed or folded, at least once where the index found it), saturated by k1 1.2;
     b is 0.1.
  Tuned on a fixed half (odd question numbers), reported on the other half and on all 60 (seed 1242, 10,000 messages, bge-m3; tune / held
  out / all). The choice on the tuning half: k1 changed nothing from 0.9 to 2; b 0 and 0.1 found one more answer than 0.2 to 0.75 (0.1
  kept, the nearer to the usual 0.75); the twelve-word cap, longest-words-first, and the weight of a prefix hit (0.25 to 1, people's plan)
  changed nothing; a title's weight and a typo's cannot be measured on this bench (messages have no title). The tuning half did not
  separate the ways of counting a word (the same word only; stems of six letters or more; stems with a length bound), so the simplest is
  kept: the same word, chosen without the held-out half. Seen on the held-out half, and not used to choose: counting by the stem of words
  of four letters or more ("przez" as "prze*" counted "przesunięty") lost a BM25 answer (q56); stems of six letters or more found one
  hybrid answer more (0.717 for all 60).

- **The exact index is not dropped:** BM25's `|||` has no every-word or exclusion semantics, so removing the `keys` index would first

- **Encrypted spaces** also match any of the plain words (founder decision, Hubert, 2026-11-12, on #1326), ranked more simply and without
  stems: their content is never in the BM25 index, so their in-memory index does it (`sealed-search.ts`): any of the words, the word being
  typed also as a prefix, a title with a typo in a word of four letters or more, and a document ranks by the words it holds, a word that
  is rarer among the audience's own documents weighing more and a word in the title more than one in the body. No stems and no accent
  folding there, so a plain space can find a document by another form of a word that an encrypted one cannot; the two answer alike for
  whole words, a prefix and quoted words or phrases. Quotes, `or` and `-word` stay exact in both. A position's score is squashed to
  (0, 1) in the plain space so that its rows and the encrypted rows merge in one order.

**Engineering choices (#1294, the optional embeddings).**

- **An overlay, off by default.** [`docker/compose.embeddings.yaml`](../../docker/compose.embeddings.yaml) adds one container,
  text-embeddings-inference `cpu-1.9.4` (by digest) running bge-m3, and points `api` and `worker` at it with `FLUX_EMBEDDINGS_URL`.
  A source checkout turns it on with `FLUX_EMBEDDINGS=on` (the launcher layers the file); a release install passes the file with `-f`.
  Without it no container runs and no variable is set. A release ships it as the `compose.embeddings.yaml` asset (coordinator call,
  2026-11-13, on #1341), its image recorded in `release.json` (`embeddings_image`). It needs about 3.2 GiB idle and 3.9 GiB at its peak (the research's
  measurement; the Compose limit is 6 GiB, because 4 GiB killed it while warming up), documented in
  [requirements](../operations/requirements.md#local-embeddings-optional).
- **Vectors in the same PostgreSQL** (pgvector, already in the database image): migration 0068 adds `search_vectors` (`halfvec(1024)`,
  cosine distance, kept in the row, no approximate index; see the hybrid ranking below), `search_vector_queue` and `search_vector_state`. The state row, written by the worker when it
  finds the container, is what switches the triggers on: until then they return at once, so a stack that never turns embeddings on
  writes no row to any of them, and the worker's first start without `FLUX_EMBEDDINGS_URL` deletes the row and empties the tables.
  A different model than the stored vectors' drops them all.
- **What is embedded:** the title and the first 4,000 characters of the body of each `search_documents` row that is not sealed (an
  encrypted space's placeholder: never embedded), is not a person, has some text and, in a space, has AI on. The last condition follows
  [AG-10](assistant.md#ag-10--ai-in-a-space) ("its content never reaches a model, including through search") and the research's table
  ("encrypted spaces and spaces with AI off are never embedded"): turning AI off deletes the space's vectors in the same transaction,
  turning it on queues its rows. The embedder is the operator's own container, never a person's connection or key.
- **A vector follows its row in the writer's transaction:** an edit of the title or body deletes the vector and queues the new words; a
  delete takes it with it (the foreign key); a row that becomes sealed loses it. The worker writes a vector only for words that still
  hash as they did when it claimed the row, under a share lock on the row and on its space's AI policy, so an edit or a switch that is
  committing cannot be overtaken.
- **No new polling.** The triggers NOTIFY `flux_search_vectors` and the worker wakes on it, as the notification generator does; it embeds
  the queue in batches of 16 until it is empty and keeps no timer while it is. A timer exists only after a failure (2 s doubling to
  60 s). An idle worker issues no statement for embeddings; a stack with embeddings off issues none at all after its first start.
- **Hybrid ranking inside `ranked`, under #1293's rule** (no statistic of the index and no row the caller may not see influences what
  they are shown): with a query vector, the one statement fuses two lists by reciprocal rank fusion, k = 60, each cut at 50 (the
  research's `hybrid_bm25`): the best 50 of #1293's BM25 **over the visible hits** (`rankedStatement`), and the 50 rows nearest to the
  query's vector **among the rows the caller may see under the same filters** (audiences, place, author, conversation, dates, task
  lifecycle), each distance computed exactly. No approximate (HNSW) index is used: its graph is built over every row of the instance and
  filters after its candidate list, so which visible rows it returns can depend on hidden ones (measured on #1341's review: at 50,000
  visible vectors and `ef_search` 100, 2,000 hidden rows near the queries changed the visible list of 4 of 20 queries; at 1,000 it
  differed from the exact list for 6 of 20). The exact list costs one distance per visible vector: about 40 ms at 50,000 at half
  precision kept in the row (170 ms at full precision in TOAST), on a single core of the review's host. Lists of 100 instead of 50 let rows
  that are only mid-list in both crowd out a first hit (measured, [research](research/2026-11-ai-context-retrieval.md#measured-in-flux-itself-1294-2026-11-13)).
  The fused score is scaled to (0, 1] (first in both lists: 1), as the BM25 rank is squashed, so an encrypted space's rows still merge
  with it, and a task named by its number keeps its added 10. The query's vector is asked of the container with a 1.5 s deadline; after
  a failure searches rank by BM25 alone for 30 s. People's search and agents' tools take it by passing one hook to `searchRows`; nothing
  else changes while it is off.
- **Recall on the bench: 0.700, not the note's 0.75** (founder decision, Hubert, 2026-11-13, on #1341: accepted as the bench result,
  recorded here against the target; no tuning on the judged questions). Measured through Flux's own statement on the research bench
  (seed 1242, 10,000 messages, 60 questions as asked, bge-m3): the hybrid's recall@10 0.700 against BM25 alone 0.583; three questions
  explain the gap to the research's own run. Depth 20 or k = 10 reached 0.75 on these same 60 questions and were not adopted for that
  reason. Measured again on #1341's review with #1293's visible-set BM25 as the BM25 list and the exact half-precision vector list
  (same seed, same container): **the hybrid 0.683, BM25 alone 0.467**, the vector list alone 0.733 (keywords 0.583 / 0.450;
  bilingual 0.667 / 0.567). The hybrid lost one question; BM25 alone lost seven (#1293's ranking, not this change). Recorded as
  measured; nothing was tuned on the judged questions.

**Costs.** The database image is about 800 MB instead of the Alpine image's 300 MB (the Debian base about 150 MB more, the `pg_search` library 282 MB). The index is about 4 MiB per 10k short
messages; a write costs about a quarter of a millisecond more (research). No new container, no new setting, no new polling.

**Revisit when** a local model that fits the 4 GB target beats BM25 on the bench, or `pg_search` changes its licence or stops
publishing Debian packages for Flux's PostgreSQL major.
