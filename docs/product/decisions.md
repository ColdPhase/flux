### F-036 — simple AI: everything is an agent

The points of #851, with the later answers applied (point 11 comes from #868):

1. **One Flux is one company** (F-037). AI belongs to a person for the whole Flux. Each space
   has its own AI switch. Guests have no AI.
2. **Connect AI once per person.** A person may hold several connections at once: a Claude plan
   (the unmodified Claude Code), a ChatGPT plan (the official Codex) and an API key, including
   the Claude Max, Ultra and Team monthly API credits. The API-key providers are F-020's list:
   Anthropic, OpenAI, OpenRouter, Gemini or an OpenAI-compatible or self-hosted endpoint
   ([coordinator default C-11](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Removing a connection pauses the agents that use it ([coordinator default C-3](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
   Together the connections power all of the person's agents. Flux sets no limits of its own and
   shows the provider's remaining usage. An API key keeps one daily budget. When a plan hits its
   limit the agent pauses until the reset and never switches to another connection (#854, #843).
3. **Everything is an agent.** Each agent has a name, saved instructions, its own model from any
   of the person's connections, and a memory of only what its owner told it to remember, which
   the owner sees and edits. An item is added only by the owner's own message ("remember
   that …") or by editing the list; an agent never adds to its memory by itself. The first agent
   is **Assistant** and answers `/ai`. More can be added, such as Planner or Reviewer (#857).
4. **Talking to your agents.** Each agent is a private conversation in Messages, with Assistant
   pinned first. `/ai` works in every conversation and is answered privately; Show everyone
   posts the answer as "Ada · via Assistant" (#842).
   - **What `/ai` may use.** Inside a conversation, only what that conversation's audience can
     see, so Show everyone never publishes anything private ([coordinator default C-12](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). In a private conversation
     with your own agent, the agent can use anything you can see. The agent's instructions and
     memory still go to the provider with a shared request ([coordinator default C-7](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)), but a shared answer never
     quotes or reveals them ([coordinator default C-8](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
   - **DMs between people.** AI is allowed there. Both people see one line, "Ada used AI here
     (Claude)", also when an agent opens a DM for its owner ([coordinator default C-2](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). No space switch governs
     DMs.
   - **Schedules** are made by telling an agent in plain words; they are listed and confirmed in
     its conversation and their results arrive there. The morning summary is one such schedule
     (#858), and the only one: the plain, non-AI summary of Notifications (#350) is removed.
5. **Tasks reach agents through their owner.** The owner gives a task to one of their agents in
   the Owner field. One setting: "When someone assigns a task to me: Do nothing / Give it to
   [agent]", with exactly one agent and "Do nothing" by default. Nobody prompts someone else's
   agent; messages from anyone but the owner are context (#856). The agent's owner or the space
   admin can **Stop** an agent working on a task, and the owner is told who stopped it. The
   admin's Stop also reaches a local client ([coordinator default C-6](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).
6. **Agents work in the task's discussion.** They talk there with other people's agents when
   both owners are among the task's people, using only what all of them can see. The task's
   people are its creator, its owner and anyone who wrote in its thread ([coordinator default C-10](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)); a message
   written by an agent does not add its owner ([coordinator default C-5](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). A question from another agent never makes an
   agent change anything ([coordinator default C-13](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Each agent's owner pays for it, sees its answers live and can
   delete them. Subtasks for other people wait for the owner's OK, with Approve all. When it
   finishes, an agent follows its "What it may do": Done with Undo, or handed back for review
   (#856, #841). Only read also hands the task back ([coordinator default C-1](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). **Review is that row:** the
   formal co-work review verdict of F-016 and F-018 is removed as a coordinator default
   ([coordinator default C-9](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)), and a separate reviewer is optional, for example a subtask for a Reviewer agent.
7. **Approvals per agent.** Each agent has one row, "What it may do": Only read, Do it and tell
   me (the default) or Ask me first. Deletions and other people's things always wait. Undo sits
   on each agent message; there is no Activity list. The Inbox holds only what needs the person
   (approvals, tasks handed back, questions), one item per agent run with Approve all; reports
   go to the agent's private conversation, never to the Inbox (#855). **Only the owner
   approves:** approving, editing or skipping a waiting item, Approve all, and accepting a
   decision happen only in the owner's own signed-in session. No agent, server or local, has a
   tool for it, not even for its own waiting item (kept from F-027's owner-only Apply).
8. **Rights.** An agent has exactly its owner's current rights: no agent project grants and no
   manager requests (#855).
9. **Code.** Server agents work only inside Flux, read the connected GitHub repository and read
   the web, and never write to either. Code changes come from the person's local Claude Code or
   Codex over MCP: one sign-in, no scopes or switches, the same "What it may do" row, and "work
   on #4" from the editor (#859).
10. **Notifications.** "Only what needs me" includes agents waiting for you, and Quiet hours is
    one row (#872).
11. **Blocked.** A task blocked on a person, a decision or another task returns to Doing by
    itself when that resolves; an agent owner resumes its work (#868).
12. **Capacity.** Flux works out how many agents run at once from the server's memory (about 2
    on 4 GB). The rest wait with "Waiting for room on the server". The operator can change the
    number in the config file; there is no setting in the app (Hubert, 2026-11-03, #860;
    [where agents run](ai-modes.md#rt-3--isolation-and-capacity)).

**What goes away:** Flux's own run limits and the seven reasons a change waits; agent project
grants and manager requests; MCP scopes, capability switches and standing grants; reactions and
background suggestions; the local waiter (#754, closed); drafts of messages to other people; the
space Agents tab; a separate "assistant" concept; the formal co-work review verdict on a pull
request head ([coordinator default C-9](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)).

### F-037 — one Flux per company, with Spaces

From #874 and the people-and-spaces answers on #861:

- **Spaces.** One flat list of Spaces replaces projects. A space can be a department, a team or
  a project. There are no group headers and no workspace switching. "Project" becomes "Space"
  in every label; internal code names may stay.
- **One workspace per Flux.** Setup creates the company. No screen, API path or document shows
  more than one workspace, although the data model may keep its workspace table.
- **Joining.** With SSO, everyone the company's identity provider lets in joins on their first
  sign-in, with no invitation; IT controls access in the identity provider. Without SSO, the
  company admin invites people with links, as F-035 describes: the admin copies a one-time link and
  sends it themselves. Flux sends no invitation email.
- **Who sees a space.** Only the people added to it. The default space **Everyone** holds the
  whole company.
- **Space settings.** A name, its people ("Add people", chosen from the company) with two roles,
  member and space admin, and an AI switch. The creator is an admin and can make others admins.
  The company admin can change any space, except an encrypted one (below; its people stay with
  its own admins, [coordinator default C-4](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). A space admin
  can also leave the space, rename it and delete it; the company admin can delete any space, but not Everyone, which holds the whole
  company. There is no global AI switch.
- **Company admins and removed people** (Hubert, 2026-11-05). A company admin's sidebar and every list from the shell hold only the
  spaces they belong to, like everyone else's, and their search and Inbox do too
  ([coordinator default C-15](#coordinator-defaults-and-inferences-not-founder-decisions-hubert-can-override)). Settings › Company holds
  the people, the company name, every space (an admin can add themselves to one, as its admin (a coordinator inference of #903), or delete it, and sees an encrypted space's name only)
  and the people who left or were removed, with **Restore**: they sign in through SSO as usual and join Everyone, and are added to other
  spaces by hand.
- **Creating a space** is one window: name, people, an AI switch (on by default) and an
  "Encrypted" switch (off by default; when on, it asks for an unlock password and offers the
  recovery code). A new space has no template and no goal and starts with Conversation, Tasks,
  Map and Wiki.
- **Encryption per space.** Chosen at creation and irreversible. An encrypted space never has
  AI. After a server restart it stays locked until a space admin enters their unlock password;
  members see "Locked, waiting for an admin", and the rest of the company works normally.
- **Who holds the keys.** Only that space's admins and the recovery code. The company admin can
  delete the space but cannot read it unless a space admin adds them. The engineering option to
  confirm: an encrypted space stays a hidden internal workspace, so F-030's code barely changes
  ([note](encrypted-workspaces.md#moving-to-per-space-encryption-f-037)).
- **No data migration.** Flux is pre-release with no installations to convert.

### F-038 — a simpler Flux

Hubert's answers 1–16 on #861 and the follow-ups of 2026-11-03, in short (each task issue holds
the detail):

- **Space views:** Conversation, Tasks, Map and Wiki from the start, with Call (formerly
  Together) in the header; every header item has a fixed slot and the view switch is one
  control at every width (#873).
- **What needs you:** the Inbox is the only list, and Home shows its top three plus "continue
  where you left off"; My tasks has a fixed place in the sidebar; the company-wide Wiki page
  goes (#865).
- **Ideas:** one word for an idea, Thought, and one for a canvas, Map. The Sketchbook becomes the
  private My map; notes become thoughts on it; Sketch, the DM Sketches tab, Drafts and Notes go
  (#866).
- **Creating:** one Create with the same types everywhere, plus "+" in Tasks, `/task` and
  "Create task" on a message. **Message actions:** Reply in thread, Create task and ⋯ (Add to
  map, Copy link, Copy text, Edit and Delete on your own); Cite, Record a result and Details go (#867). Copy text on every
  readable message: founder direction 2026-11-08.
- **Tasks:** Board and List have the same controls; cards have no ⋯; empty sections are hidden;
  one discussion per task, where agents write too. Statuses are To do, Doing, Blocked and Done;
  "Not pursued" becomes Done with a "dropped" note. Blocked waits for a person, a decision or a
  task and returns to Doing by itself. The Result object goes; Done takes an optional "what came
  of it" line (#868).
- **Wiki:** edited in place on the rendered page, versions saved automatically, History under
  ⋯. There is no pages column: the page title is the page switcher ("Lending rules ▾"), which
  opens a list of the space's pages with search and "+ New page", in the same place with 1 page
  or 50, and the Wiki keeps to two columns, sidebar and page (Hubert, 2026-11-03). A small
  "Contents" button (≡) next to ⋯ opens the list of the page's headings, and a click scrolls to
  that section. It stays in the same place on every page and shows "No headings yet" when there
  are none; there is still no "On this page" column (Hubert, 2026-11-03). Raw Markdown editing,
  version reasons and Draft/Published go; live co-editing keeps working (#869).
- **Search:** ⌘K and the Search page are one tool, grouped by kind, with no filter chips (#870).
- **Words:** visibility text only where the audience differs from the place's default; one word,
  "Decision"; plain sentences instead of "Replaces" and "In the Wiki". Accepting a decision that
  replaces another only marks the old one replaced; Flux no longer moves or parks tasks (#871).
- **Settings:** one list of sections on every device (Account, Appearance, Notifications, AI,
  the company section, Shortcuts) in visual direction A. Notifications are one level (Only what
  needs me, Everything, Nothing) plus email to one or more confirmed addresses, and Quiet hours
  is one row. Focus mode goes, and so does the plain, non-AI morning summary (#350): the only
  morning summary is a schedule you ask an agent for. The account menu holds only the name,
  Settings and Sign out (#872).
- **Motion** (after the motion audit, #863; stated precisely by Hubert, 2026-11-03): one rule set
  for all of Flux.
  - A view switch shows the new screen at once, with at most a 120 ms fade-in. This supersedes the
    crossfade of #593 and #719 ([motion guide](../design/motion.md)).
  - Press feedback is colour only, with no spring. Small controls may scale to .98; rows and cards
    never scale. This supersedes §2 of the [Prostota guide](../design/final/README.md) (scale
    0.97 and a spring back).
  - Feedback arrives within 100 ms. Surfaces (panels, dialogs, menus, sheets) open in 180 ms and
    close in 120 ms, with no springs and no scale, and they open with their content. One action
    makes one motion. Nothing animates on first appearance or on a refetch.
  - #863 updated `docs/design/` (the [motion guide](../design/motion.md), through #876). The application
    differs from it until #863's fixes land.
- **Fast and light** (Hubert, 2026-11-03, [#862](https://github.com/ColdPhase/flux/issues/862)):
  Flux must feel quick on a VPS with 2 vCPU and 4 GB RAM, for a team of a few people with a few
  server agents.
  - **Targets for that host:** idle at most 2% CPU and 100 database statements a minute; an open
    tab at most 4 requests a minute; a navigation at most 8 requests, with no repeats, and
    content within 500 ms; server p95 at most 50 ms; at most 250 KB on a first visit before
    content; an image of at most 250 MB; a restart in at most 5 s. The performance run gains a
    CPU-limited phase that guards them.
  - **Instant actions.** Your own action (send, Done, moving a task) shows at once and the server
    confirms it in the background. If that fails, the previous state returns with "Couldn't
    save · Try again".
  - **Live updates.** Other people's changes arrive as a push over the existing live connection,
    replacing the 15–20 s polling. After a reconnect Flux does one catch-up fetch.
- **By the standing UX rules:** one plain label per thing on every device, and AI words leave
  everyday screens.

The design guide (`docs/design/final/`) was updated through #864 (#876) to the mockups Hubert
approved on 2026-11-03. Where a later decision differs from the guide, the decision wins and the
guide is corrected.

### Constraints and risks, with dated sources

- **Anthropic: plan credentials** (code.claude.com/docs/en/legal-and-compliance, retrieved
  2026-11-02). Third parties may not "collect, store, or intermediate Claude.ai credentials or
  session tokens" or route requests through Free, Pro, Max or Ultra plan credentials on behalf of
  their users. The same page: "Nor does it prevent an end user from signing in to the unmodified
  Claude Code binary with their own Claude subscription, including where a platform hosts
  Claude Code", and Anthropic may act "without prior notice". So Flux runs only the unmodified
  CLI, never handles a plan token and never impersonates Claude Code. Anthropic's new Usage
  Policy takes effect on 2026-11-12; re-read both pages then.
- **Anthropic: monthly API credits** (support.claude.com/en/articles/17154008, new on 2026-10-07,
  retrieved 2026-11-02). Max, Ultra and Team plans include monthly API credits for an API key from
  the linked Console organization. "API requests stop until your next monthly credits arrive.
  Usage is never charged to your Claude plan." Free, Pro and Enterprise are not eligible, and
  only one organization can be linked. Flux offers them as an API key and calls them "API
  credits".
- **OpenAI: hosted teams** (developers.openai.com/siwc, retrieved 2026-11-02, no page date).
  "These docs explain ChatGPT plan usage for open-source and locally hosted apps. If you're
  interested in offering it in a paid or remotely hosted app, complete the interest form." Flux
  uses the Codex CLI's own device sign-in, not Sign in with ChatGPT, but a team-hosted Flux may
  count as remotely hosted. Recorded as a risk.
- **Server capacity.** Flux must feel quick on a VPS with 2 vCPU and 4 GB RAM for a team of a
  few people with a few server agents (Hubert, 2026-11-03, #862; the targets are in
  [F-038](#f-038--a-simpler-flux)). Always-on agents need capacity per person, measured against
  that target (#860). Flux computes how many agents run at once from memory (about 2 on 4 GB);
  the rest wait, and the operator can change the number in config (Hubert, 2026-11-03, #860).
- **Web reading** (#918, built 2026-11-07; the mechanism is an inference of the agents, for push-back). Read-only page reading
  is a Flux tool, `flux_read_web`: the Flux server fetches the page, GET only, public addresses only, bounded in time and
  size, with the guard of link cards (F-031).
  The same tool serves a server run on either engine (not a local client: it reads the web with its own tools, and has no request
  that Flux could check an address against, #953), and the runtime's egress stays what it was
  (the vendors' hosts and Flux's route): a CLI's own web tools would need every public host open through a TLS tunnel, which cannot be
  held to read-only. Every address the server sends a request to for a run is recorded before the request goes out, those that failed too, and the run ends with the list, in Flux's words (under its answer, or in its end line when it has none). It is off unless the operator
  sets `FLUX_WEB_READS=on`, like every other outbound path. Web search needs a search provider that no install has by default and is not
  built yet. **The risk, recorded:** the open web can try to instruct an agent (prompt injection), and an address the agent chooses can
  carry what it knows to the site's logs (shown in the review of #949), so an agent reads only addresses it was given (C-30). Web content is data. Rights, waits, the never-list and Undo are the defence: only the owner
  instructs; deleting and other people's things always wait; there is no tool to approve a waiting item, to change access or to send
  anything out. `tests/app/web-content-cannot-bypass-approvals.test.ts` shows that a page, and another person's task title that
  becomes a run's request, cannot make an agent act beyond "What it may do" or skip a wait.
- **Reference: Hermes Agent** (Nous Research, `NousResearch/hermes-agent` at `d9f15af4`,
  reviewed 2026-11-02). It has one model picker, one always-on gateway and almost no limits of
  its own. Its core Claude route poses as Claude Code, and Flux must not copy that.
