## #315: the multiple-provider bundle is excessive; account migration is not

**Observation.** `IdentityConfig.oidc` is a single optional `OidcConfig`, not a provider collection ([config.ts:15](../../../app/apps/server/src/identity/config.ts)). The provider ID is derived from issuer; `oidcUser` requires the configured issuer, a subject and verified email, and returns the subject as identity ([auth.ts:35](../../../app/apps/server/src/identity/auth.ts)). Implicit email linking is explicitly disabled at line 98. This already matches one IdP per installation.

The old S5b groups five different concerns: password switch, a multi-provider file, linking/unlinking, Entra/Google claim profiles and operator identity re-keying ([historical contract at the source pin](https://github.com/ColdPhase/flux/blob/9d54135b7b13f6c932ccf4c6e080ae4ae48d2fa5/docs/product/mcp-identity.md#L1055-L1062)). Only the provider collection and combined-standing rules are inherently multi-provider features. **“Profiles” here are provider claim adapters, not personal user profiles.** One installation using Entra can need Entra claim handling just as much as an installation listing several providers. Do not delete verified-email/issuer/subject rules or pretend every generic OIDC issuer has identical claims.

**Real retained journey.** A person creates a local Flux account with private notes, project roles and agents; the operator later enables its sole SSO provider. F-024/#313 promises that a verified-email collision tells the person to sign into their existing account and link the provider; the unverified collision also offers linking or address claiming ([collision rules](../mcp-identity.md#password-sign-up-reset-and-email-collisions)). Deferring the only documented conversion flow while retaining that instruction leaves a dead end. A new SSO account is not equivalent to preserving the old account's data, roles and provenance.

**Inference/recommendation.** Keep a narrowly specified conversion to the configured IdP, with proof of the existing account and the new provider identity, unique issuer/subject binding, audit and appropriate session/grant consequences. Alternatively provide an explicitly supported operator recovery path and change the guidance; do not promise a nonexistent Link button. Do not introduce automatic email-based merging. The auth bridge forwards Better Auth endpoints, so inventory the pinned framework's explicit-linking endpoints rather than assuming a lack of Flux UI means they cannot be called.

When SSO is selected as the installation's login mode, a local-password route must not silently bypass that decision. Existing `emailAndPassword.enabled=true` and `autoSignIn=true` are observations, not delivery of SSO-only mode. Preserve unmanaged/local-password mode when no SSO is configured, and record a bounded operator recovery method. Managed-account password/reset protection already belongs to #313; coordinate the additional installation-wide password-off behavior there or in narrowed #315 rather than duplicate it.

**Cost saved.** No provider arrays, multiple login buttons, per-account combined-standing policy, general unlink UI or multi-provider migration framework. Claim support should cover the selected supported provider truthfully; adding every vendor profile is not automatically a v0.1 requirement.

**Disconfirming evidence / revisit.** An enterprise demanding simultaneous independent IdPs, broker-free federation or an actual migration across issuers would justify reopening multi-provider work. Existing-account conversion and an explicitly supported Entra installation already justify some single-provider safeguards; one IdP alone does not make all S5b concerns unnecessary.

## #316: standing checks and fresh human confirmation solve different problems

**Observation.** `createSessionResolver` accepts a currently valid session and exposes principal, session ID and expiry; it exposes no proven last human authentication time ([session.ts:32](../../../app/apps/server/src/identity/session.ts)). Creating a standing action grant calls `sessions.requirePrincipal` plus the existing rights/use-case checks ([routes.ts:48](../../../app/apps/server/src/agent-connection/routes.ts)). Connection creation and execute consent likewise have Flux scope/connection binding, but no Flux recent-authentication guard. `oidcUser` currently discards `auth_time`; the callback's token verification alone does not add a freshness policy.

**Inference.** Someone controlling an unattended or stolen valid browser session can reach authority-creating paths as that principal. Current origin/CSRF checks, client/connection binding and ACLs are valuable, but are not independent proof that the owner just authenticated. #311's successful offline refresh confirms the IdP still serves the account. It does not prove the owner re-entered credentials; neither a new token's issue time nor a newly created browser session is a substitute for `auth_time`.

**Standards fact.** OIDC defines `max_age` as the allowed elapsed time since active user authentication; when requested, the ID token must contain `auth_time`. These mechanisms support a narrow freshness check. **The ten-minute value is Flux policy, not a universal OIDC mandate.** [OpenID Connect Core §3.1.2.1 and §2](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest).

**Retained boundary.** Apply recent proof when a human creates/increases lasting agent authority: execute consent, a new standing grant, and identity conversion if offered. Bind a successful re-authentication to that account/session/intended action and preserve the signed OAuth continuation. Do not prompt on tool calls, routine background work, token refresh, reconnect, revoke or a strictly narrower grant. That would defeat the authorized cooperative-agent workflow.

For an IdP that cannot return/verify the requested freshness, report the exact supported assurance. A silent SSO round trip proves current account participation, not necessarily recent credential entry. Do not silently relabel it as stronger proof or use an undocumented password fallback on a managed account. A configured provider with appropriate fresh-auth support can reuse the existing provider flow; no general multi-provider framework is needed.

**Cost/security trade-off.** This adds occasional human re-authentication at a small set of consequential boundaries and preserves normal autonomous work. It reduces persistence gained from an old valid session; it does not eliminate malware or active-session compromise. Read-only delegation also exposes data, so narrower scope is prioritization, not a claim that read consent is risk-free.

**Disconfirming evidence / revisit.** If every authority-creating operation is independently proved to pass a fresh-authentication policy already enforced by the sole IdP and validated by Flux, a duplicate Flux guard is unnecessary. Current code supplies no such evidence. Broader sensitive-action coverage should follow a concrete requirement, not expand to every button.

## #317: the specified owner clients can use OAuth without a second key system

**Observation.** Flux currently offers authorization-code and refresh grants ([auth.ts:105](../../../app/apps/server/src/identity/auth.ts)). `/mcp` uses `requireMcpAuth` with Flux issuer/audience validation and rechecks the current owner connection/grants ([mcp-route.ts:56](../../../app/apps/server/src/agent-connection/mcp-route.ts)). The Connect guide specifies OAuth-capable clients ([ClientGuide.tsx:33](../../../app/apps/web/src/agent-connection/ClientGuide.tsx)). There is no Flux `fxk_` key implementation in these paths.

**Vendor fact.** Current Claude Code documentation describes `claude mcp login` over SSH: authorize in a local browser, then paste the redirect into an interactive SSH terminal. It also states a non-interactive run cannot initiate that sign-in itself and must be authorized from an interactive session. Thus remote location alone does not require an opaque Flux key. [Claude Code remote MCP authentication](https://code.claude.com/docs/en/mcp#authenticate-from-the-command-line).

**Inference/recommendation.** Existing Flux personas are owners who connect their clients, authorize scope and let those clients continue. Retain the actual SSH/callback workflow, including tests for the pinned real clients, in the basic OAuth delivery. The proposed key feature adds a second mint/store/list/expire/revoke/standing-check path, operator switches and another secret users can misplace. No admitted v0.1 CI job or mandatory header-only client establishes the need for it. State the unsupported case honestly rather than claim every generic client works.

**Important counter-evidence: machine authentication is technically available.** The official [OAuth Client Credentials extension](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials) documents application-level authentication; the [official TypeScript SDK example](https://github.com/modelcontextprotocol/typescript-sdk/blob/b022522089a0c8b632595c6e7b536453945ed5a9/examples/oauth-client-credentials/README.md) demonstrates it. It authenticates a service as itself, whereas Flux F-019 currently binds delegated actions to an owning person and their grants. Supporting it would need an admitted machine-principal/authority/payer contract, not merely a pasted bearer secret.

**Status discrepancy, dated and pinned.** Direct GitHub inspection of `modelcontextprotocol/ext-auth@fb374c7db2b34f18ca9183882e0beecdf661892b` (commit 2026-06-18) still lists Client Credentials under Draft and labels its normative file “Protocol Revision: draft”; the current extension documentation and [official March 2026 overview](https://blog.modelcontextprotocol.io/posts/2026-03-11-understanding-mcp-extensions/) describe it as available/live. TypeScript SDK main was pinned to `b022522089a0c8b632595c6e7b536453945ed5a9` (2026-10-05), with provider/examples present. **Do not justify #317 cancellation by saying the mechanism does not exist, or by relying on an unqualified draft/stable label.** The reason is the current product's owner-only model and lack of a concrete consumer.

**Revisit condition.** A required unattended CI service or pinned header-only client that cannot complete supported OAuth could justify a new bounded choice between owner-bound expiring keys, client credentials, or another supported mechanism. Evaluate exact client behavior, principal/grants/revocation, custody and compatibility then. This does not justify making key management part of every person's onboarding now.
