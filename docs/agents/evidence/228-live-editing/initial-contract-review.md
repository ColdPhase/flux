## Required corrections

### C1 — Define replay identity and supported replica enrollment

Proposal lines 190–204, 223–225 and 253–259 specify actor-bound replica IDs and deduplicated (actor, update UUID) receipts, but do not define immutable payload identity, receipt namespace, or durable replica enrollment across socket/process/browser recovery.

Reproduction of the ambiguity: an update UUID is acknowledged, its reply is lost, and a reconnect submits the same UUID with different binary bytes or against another generation. A deduplicator permitted by the present wording could return success for bytes that were never admitted, or reuse an actor's receipt from another room. A restarted browser can also produce fresh clocks under a previously used replica ID if persistence is treated as permission to keep generating under that ID.

Record a receipt key scoped to canonical resource/room, generation, authenticated actor and command UUID, with an immutable payload fingerprint and original admitted result/sequence. Changed payload, room, generation, or Save snapshot request under the same key must receive a typed idempotency conflict. Exact retries must recheck current authority before returning protected content. Save fingerprints must include expected material version, live generation, acknowledged head/hash and deliberate metadata. Receipt/checkpoint compaction must retain enough identity to enforce this.

Specify how a new Yjs replica becomes enrolled before producing local structs, how ownership survives server restart, and how an old encoded pending bundle can be replayed without issuing new structs under a reused session ID. [Official Y.Doc documentation](https://docs.yjs.dev/api/y.doc) labels clientID readonly and warns against reuse across sessions. Therefore a server-selected assignment to clientID must not be assumed to be a supported stable API. A server-owned enrollment of a freshly generated ID is a candidate; its collision, multiple-tab, restart and pending-recovery behavior belongs in the mandatory spike. Do not assert forensic character attribution: the actor/update ledger in lines 217–221 correctly avoids that claim.

### C2 — Make continuous/coalesced latency samples unbiased

Proposal lines 110–123 permit 25/s movement and coalescing; lines 271–285 require a matching rendered state for continuous trusted inputs. An older pointer position or preview can legitimately be superseded before the peer paints it. Literal equality can then wait forever; omitting those samples can manufacture a low p95.

Define generation/sequence correlation, a fixed sampling schedule chosen before the run, the treatment of superseded movement/preview inputs, and a finite timeout. For replaceable state, a sample may end when a rendered later sequence from the same active interaction covers its input, while the report also records publication cadence and superseded counts. For committed map commands and text, prove the sampled command/update is included in the rendered confirmed head. Record every scheduled sample, timeout/error and overload; timed-out samples cannot disappear from the distribution or pass as successful latency. Require continuous pointer movement/typing during the measured interval, not only isolated spaced inputs that avoid batching.

The single-driver monotonic clock and two-rAF peer reporting in lines 271–278 are acceptable as a conservative observation of DOM state after a paint opportunity. They do not prove physical pixel presentation. Keep the negative controls, raw samples, overhead control without subtraction, and visible recording. At the 100,000-code-unit body limit, specify replacement/delete-then-insert fixtures and a separate over-limit rejection/recovery fixture; do not raise the existing limit to accommodate continuous insertion.

Clarify that once-per-second presence renewal is a heartbeat/expiry budget, not a one-second cap on changing cursor/selection delivery. Named cursor movement must be exercised during continuous typing before Save.

### C3 — Distinguish rollback from uncertain COMMIT

Proposal line 201 says failed commit yields no success or shared bytes; lines 258–259 correctly require lost-reply receipt repair. These need one consistent rule.

Reproduction: PostgreSQL commits the journal/receipt, then the connection drops before the API observes the COMMIT response. Treating that exception as proof of rollback can reset confirmed state or falsely tell the editor its work was never shared.

Record that a definite rollback produces no admitted journal entry/ACK/fanout. An uncertain outcome returns a recoverable pending/unknown result and reconciles the immutable receipt under current authorization and the same generation/serialization boundary; it must not delete/reset confirmed data. Fanout reads only committed records. Include both injected definite rollback and lost COMMIT response in the persistence spike, followed by two API instances/restart/exact retry. A client is Synced only after the original receipt is established, and Save cannot succeed while its pending update outcome is unresolved.

## Architecture and integration assessment

The transport choice is supported by current source: app/apps/server/src/index.ts:73–74 registers the stream WebSocket server through streamUpgrades with maxPayload 1024; :95–98 is the single upgrade dispatcher, currently media first then stream. app/apps/server/src/live/signal-gate.ts:64–66 already creates a separate noServer ws server with its own payload bound; :164–183 authenticates/origin-checks before upgrading and claims only media paths. The proposal's separate 65,536-byte editing server is credible if routed through this owner. [ws primary documentation](https://github.com/websockets/ws#multiple-servers-sharing-a-single-https-server) supports the single dispatcher pattern. [Fastify's documentation](https://github.com/fastify/fastify-websocket#attaching-event-handlers) requires synchronous handlers before asynchronous work and places post-upgrade messages outside ordinary HTTP handling. Those facts do not prove the new gate's behavior.

Native authority remains a good boundary. Map commands already serialize mutations through the sketch/policy path; moveThoughts at app/packages/core/src/sketches/service.ts:333–356 checks all selected versions before any move. Conditional undo must retain expected resulting versions and link postconditions rather than reuse the current client conflict retry. Remote deltas must cover rename, add/update/move/remove thought, add/remove link and promotion/copy, including agent composition, without generating events for previews.

The wiki fence can be implemented at the shared core boundary. HTTP update and Add to docs call updateDoc/addSection (server/docs/routes.ts:68–78); both currently append versions under the material lock (core/docs/service.ts:280–322; db/repositories/docs.ts:61–64). MCP calls the same core updateDoc through nativeDocsInEventSession (server/agent-connection/doc-actions.ts:50–57; server/docs/adapters.ts:42–44). Generic material updates explicitly reject doc kinds (server/conversation/store.ts:349–350). Place the fence before no-op returns and source-link mutations, including metadata-only updates. Require an inventory test over every writer, rather than only route-specific guards. Preserve the existing access lock order before material/live-head locks.

Yjs convergence is supported, but payload safety is not proved by ordinary body-length checks. [The pinned export source](https://raw.githubusercontent.com/yjs/yjs/v13.6.27/src/index.js) exports decodeUpdate and content classes. [The decoder source](https://raw.githubusercontent.com/yjs/yjs/v13.6.27/src/utils/updates.js) exposes decoded structs and delete ranges; parent identity can be inferred from origins rather than explicitly encoded. [The apply source](https://raw.githubusercontent.com/yjs/yjs/v13.6.27/src/utils/encoding.js) retains unresolved structs and deletion ranges for later application. These are evidence for a spike, not proof that the proposed validator exists. Stable v13 and a compatible binding are the right candidate: [the binding's primary README](https://github.com/yjs/y-codemirror.next) explicitly separates its unstable v14 development branch from the stable package.

Own undo through narrowly tracked origins and relative cursors is plausible under [UndoManager](https://docs.yjs.dev/api/undo-manager) and [relative-position](https://docs.yjs.dev/api/relative-positions) APIs. Unresolvable or wrong-body positions must be hidden, never mapped to another room. Initialization, remote sync and compaction must not enter local undo. Saved-by plus contributing actor/update intervals, immutable citations and saved-version-only exports/agent sources are appropriate provenance boundaries.

## Mandatory bounded calibration gates

1. **Transport fixture:** use the actual single dispatcher with media both enabled and disabled. Demonstrate immediate first frames are handled, editing accepts the candidate 64 KiB message boundary and rejects larger messages, the existing stream still rejects >1024 bytes, paths never reach two handlers, Origin/session refusals occur before protected bytes, and tracked shutdown closes all three paths. Record explicit assembly/worker/per-connection/server aggregate caps before running it.

2. **Stable codec/replica fixture:** pin exact compatible dependencies and one Yjs instance. Using public stable exports, reject extra roots/types/attributes/embeds/subdocs, spoofed replica ownership, cross-room/generation payloads, inconsistent duplicate struct content, unresolved origin/parent/clock gaps and out-of-range/future deletes without mutating confirmed state. Test bundles where forbidden state becomes visible only after a missing dependency arrives. Exercise maximum body/bytes, Unicode/IME, worker timeout and termination, concurrent tabs, restart enrollment, checkpoint/compaction and pending replay. The proof must cover the complete candidate graph/delete dependencies, not just resulting body.toString(). If the guard cannot be demonstrated, independently reconsider the stated OT alternative.

3. **Authority/persistence fixture:** two API processes share PostgreSQL. Barrier-controlled races cover lease/native map CAS, stale final drag, conditional own undo with intervening links, Save/live update, dirty and clean HTTP/MCP/section/metadata writers, definite rollback, uncertain commit, missed NOTIFY, restart, exact/altered retry, and retained provenance. NOTIFY is a wake-up only; [PostgreSQL documentation](https://www.postgresql.org/docs/17/sql-notify.html) establishes commit delivery and limited payloads, not durable client replay. Define a server delivery linearization point and prove revocation is serialized with dispatch. A separate recheck followed by an unlocked send is insufficient: current stream/delivery.ts:93–101 illustrates that gap. Discard application-queued output, stop new content admission and fence old generations; explicitly distinguish previously authorized bytes already handed to the transport.

4. **Actual-path latency/interaction fixture:** use the corrected sampling contract and original 50/500-thought, 10k/100k-code-unit fixtures, trusted browser inputs, both editor and ordinary live reader, named cursor/selection, multi-drag, simultaneous writers and own undo. Retain the proposed p95 ≤200 ms healthy-local gate; record 30 warmups, at least 200 scheduled samples over at least 60 seconds per scenario, raw distributions/errors/queues, ACK/render segments, commit/dependency/environment pins and negative controls. The 40 ms batching, 1 MiB windows and 8 MiB checkpoint are calibration candidates, not measured capacity promises. Long edit/delete history and compaction must fit or surface a truthful recoverable limit; a shortcut bypassing database validation or safe preview does not calibrate the proposed path.

These gates authorize bounded non-production evidence after the four corrections; they do not authorize a performance claim or weaken the integrated user outcome. Fresh independent assessment must accept the corrected document, then fixture pins/caps, before production implementation.
