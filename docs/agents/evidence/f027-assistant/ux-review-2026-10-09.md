# UX review: the in-Flux assistant (AST-10 journeys, copy, wireframes)

- **Reviewer:** independent UX evaluator. I did not write this design.
- **Reviewed:** `origin/claude-hubert/assistant-design`. The proposal is at `90d73dff`
  (`docs/product/research/2026-10-09-assistant-proposal.md` §5). The decision text
  appeared during the review at `6fe8e155` (`docs/product/assistant.md`). Its AST-10 is
  byte-identical to proposal §5, and AST-1 to AST-9 differ only in headings and links.
  The decision also adds *Terms*, which defines "Yours". Findings apply to both commits.
- **Compared against:** `docs/design/final/README.md` (F-026) and the canvas renders
  `desktop-agents`, `desktop-appearance`, `phone-agentdetail`, `desktop-panel`,
  `desktop-inbox`, `desktop-handoff`, `desktop-tasknotice`, `desktop-home`,
  `phone-agentthinking` and `desktop-conversation`. Also checked: the Notifications
  morning summary shipped by #350 on this branch, F-022's sign-in console and O-008 §6.
- **Method:** a review of the design documents only. No assistant screen or run exists to
  exercise yet, so I verified no interaction, accessibility or timing. AST-10.12's
  review on the running app is still required.

## Verdict

**Accept the direction, with changes required before A7 is built.** The core ideas
are right and close to excellent. These include the two-option approval control, the
five plain switches, the "always waits" list, one result line per run with Undo,
failures with a fix in place, and reactions from a fixed set that fold into existing
Inbox items. The founder's switches, default mode, schedule rules and account order
are all kept.

It is not yet "surprising". Five problems would break the first minute or the
messenger promise for real people:

1. Sign-in is actually a terminal.
2. The first request can fail because the assistant is not in the project.
3. There are two different "morning summaries".
4. There is no private way to talk to your own assistant.
5. Colleagues are shown things that are untrue about what AI does in their project.

All five fixes are small and use patterns already on the canvas.

## Tap counts (as designed)

| Task | Taps | Note |
| --- | --- | --- |
| Turn on, first time, from the Home card | 6 Flux taps plus the vendor's steps | Set up, Claude, Open claude.ai, paste (2 on a phone: long press, then Paste), Enter, Turn on |
| Turn on, already signed in | 4 from anywhere | Settings, Agents and AI, *Ada's assistant*, switch |
| Allow Wiki edits | 0 by default; 2 from a failure line | *Allow Wiki edits*, then *Try again* |
| Morning summary | 2 on the assistant screen; 5 from anywhere | It also duplicates Settings → Notifications (P1-3) |
| Undo a change | 1 in the line; 2 from Activity | Good |
| Review a waiting change | 2 | *Review*, then *Apply* |
| Stop a run | 1 | Good |
| Turn the assistant off | 4 | There is no shortcut on the assistant's own panel (P3) |

## Findings

### P1: fix before A7 starts

**P1-1. The sign-in is a terminal, and the ChatGPT path is not drawn.**
- **Where:** Journey 1 step 3. AST-1 relies on F-022's console, which is xterm.js over a
  PTY whose output is "shown as is" (change list, #279).
- **Problem:** Ada expects "one sentence and the official sign-in". What she gets in the
  first minute is CLI text such as `Paste code here if prompted >`. The ChatGPT choice
  uses a device code (`codex login --device-auth`), which goes in the opposite direction:
  she types a code on chatgpt.com. Nothing in the design draws that path. F-022 also notes
  that device-code sign-in must first be enabled in ChatGPT's security settings. Most
  people will hit that wall, and Journey 6 has no row for it.
- **Fix:** Draw both sign-ins as guided cards. Keep the terminal folded under *Show
  details*. The supervisor recognises only the sign-in URL and the device code in the
  CLI output, in memory and for display only. This needs one line in AIM-3, because
  N2 says Flux never parses console frames.
  - **Claude:** "1. Open claude.ai and approve. 2. Paste the code here."
    `[ Open claude.ai ]` `[ Paste ]`. The *Paste* button reads the clipboard on tap,
    so it is one tap on a phone. The pending sign-in survives a PWA reload while
    the code is valid.
  - **ChatGPT:** "Enter this code on chatgpt.com: **ABCD-1234**" `[ Copy and open
    ChatGPT ]`. Flux notices when sign-in finishes; there is no paste.
  - **New Journey 6 rows:**
    - "ChatGPT needs one setting first: turn on *device code sign-in* in ChatGPT →
      Settings → Security." `[ Open ChatGPT settings ]`
    - "That code has expired. Codes work once, for a few minutes." `[ Get a new code ]`

**P1-2. The first request can hit "I'm not in this project yet", and non-managers reach a dead end.**
- **Where:** Journey 1 steps 4–8, and Journey 6, row "Not in the project". AST-3
  says a project manager grants the assistant its project access.
- **Problem:** Journey 1 goes straight from *Turn on* to a result, but nothing adds the
  assistant to the project. A member who is not a manager is told only "A project
  manager can add me in Agents", with no button to press. In the shared projects that
  are the main case, the first impression is a refusal.
- **Fix:**
  - *Turn on* also adds the assistant to every project where the owner is a manager.
    The ready card adds the line "It joins the projects you manage. In others, a
    manager adds it."
  - Show the starter chips only where the assistant is already in the project.
  - For a non-manager, replace the dead end with `[ Ask Jonas to add me ]`. This
    creates the existing Agents row "Request · Ada's assistant asks to join ·
    Review ›" in the manager's Inbox. The result line then reads "Asked Jonas to add
    me. I'll do this when he does."

**P1-3. There are two morning summaries, and one of them duplicates the Inbox.**
- **Where:** Journey 4, the *Scheduled* starter "Morning summary at 9:00", and
  AST-7 Output.
- **Problem:**
  - Settings → Notifications already has **Morning summary** (#350, S22, on this
    branch): one push at 09:00, "3 things wait in your inbox". By design, it is not an
    Inbox item.
  - The assistant adds a second "Morning summary" at 9:00. It has its own time
    setting and its own push, and it creates an Inbox item that lists things already
    in the Inbox.
  - Ada would get two pushes at 9:00 with the same name, set in two places. The
    Inbox would also break S1, which says the Inbox holds only what needs you.
- **Fix:** keep one morning summary.
  - The assistant starter reads "( Let your assistant write your morning summary )".
    It turns on the Notifications summary and takes its time from there. There is
    still one push, and the assistant writes its text.
  - The summary is never an Inbox item. Its place is one line under the Home
    greeting: "Good morning, Ada. Jonas is waiting on you for #8, and 2 tasks are due
    today. ›".
  - Settings → Notifications → Morning summary shows "Written by Ada's assistant ·
    Change ›".

**P1-4. There is no private place to talk to your own assistant.**
- **Where:** Journey 2 step 6 (`⌘K` "Ask my assistant… in the current place"), the
  agent page's **Message** button on the frozen canvas (`phone-agentdetail`,
  `desktop-agents`), and Home jobs that "report only to you … on Home".
- **Problem:**
  - Every request is public: "Everyone in the project sees what she asked." Ada
    cannot ask "Is Jonas's plan realistic?" or "Draft a polite reply to Jonas" without
    her colleagues seeing it.
  - `⌘K` from Home or Inbox has no "current place" to send to.
  - The canvas's *Message* button on the assistant's page leads nowhere.
  - In a messenger, a personal assistant without a 1:1 chat feels like a bolted-on
    feature.
- **Fix:** *Message* on the assistant's page, and `⌘K` → "Ask my assistant…" outside a
  project, open **You and your assistant**. It is a private conversation listed under
  Messages, using the existing DM pattern.
  - It reads the projects chosen for the assistant.
  - Any change it makes still appears in its project as "Ada's assistant … · asked by
    Ada", without quoting the private request.
  - Home job results and plain-text drafts land there.
  - This needs a one-line exception to O-008's DM rule. That rule protects the other
    participant, and here there is none.

**P1-5. Colleagues are told something false about AI in their project.**
- **Where:** On the canvas's Agents tab, the row reads "Project policy · agents read and
  propose; people accept" (`desktop-agents`). Journeys 1 and 2 label messages only
  "Agent · for Ada". O-008 §6, still in force, requires the answer's provenance to name
  the provider for its audience.
- **Problem:**
  - Jonas reads "agents propose; people accept", then watches Ada's assistant rename
    and create tasks directly.
  - He is never told that his messages were sent to Anthropic under Ada's personal
    plan settings.
  - Both damage trust in the "AI and people together" pillar.
- **Fix:**
  - The policy row tells the truth: "Agents read and propose; people accept.
    Assistants also edit for their owner, with Undo." Its sheet gets one choice,
    "Assistants in this project: [ Edit for their owner | Only suggest ]". It
    compiles into the assistant's project grant, and with *Only suggest*, Ada's
    edits become suggestions.
  - Every assistant message meta shows the provider: "Ada's assistant · Agent · for
    Ada · Claude".
  - The panel that other people see says "Uses Claude through Ada's account. What it
    reads here goes to Anthropic."

### P2: fix in the slice that builds it

**P2-1. The answer and the result line say the same thing, and the line loses the canvas's object rows.**
- **Where:** Journey 1 step 8 (five lines: two of prose, then *Done*, then *Waiting*),
  Journey 2 step 3, and "Result lines".
- **Problem:**
  - "I gave three tasks clearer titles…" repeats "Done: renamed 3 tasks…".
  - The prose line "made task #12" drops P5's task row (state glyph, number, title,
    owner), which colleagues use to scan the stream.
  - Nobody can see *what* a rename changed without opening every task.
- **Fix:** one bubble per run, following principle 3 ("Everything belongs to its
  message").
  - The bubble opens with the P5 notice header, "Ada's assistant renamed 3 tasks and
    added done-when to 4 · Undo", followed by up to 3 object rows and "+4 more ⌄".
  - Prose appears only when it adds something: a reason or a question.
  - Expanded rows show before and after: "~~Probes~~ → Calibrate the probes at two
    depths". A Wiki edit shows "2 paragraphs changed · See changes".
  - *Review* shows the same diff.

**P2-2. Others see "@My assistant".**
- **Where:** Journey 1 step 6 and Journey 2 step 2.
- **Problem:** Jonas reads "@My assistant tidy this project's tasks" and cannot tell whose
  assistant it is, or whether it is his.
- **Fix:** For every viewer, the mention chip shows the agent name "Ada's assistant".
  "My assistant" is only the label in Ada's own `@` list. Typing `@my` finds it.

**P2-3. The run is invisible to colleagues, so they collide with it, and queueing is undefined.**
- **Where:** Journey 1 step 7, and the edge cases of a conflicting edit, two assistants at
  once, and a background run during a request.
- **Problem:**
  - O-008 sends progress only to the owner. Jonas may edit #4 while Ada's
    assistant renames it, and nothing says what happens to that change.
  - With one lane per owner, a request made at 9:01 can sit behind a 10-minute
    morning job with no explanation. A second request during a run also has no copy.
- **Fix:**
  - Everyone sees "Ada's assistant is working…". Only Ada sees the detail and Stop.
  - A write that fails the version check becomes a result item: "Skipped #4: Jonas
    changed it while I worked · Open". The same applies to "Jonas's assistant
    changed it…".
  - A request behind a background run shows "Finishing your *Morning summary* first.
    Yours starts next. [ Stop the summary ]". Owner requests always take priority.
  - A request behind another request shows "Next: 'turn this into tasks'. It starts
    when this one ends · Cancel".

**P2-4. Waiting changes from a conversation can expire unseen.**
- **Where:** AST-5, under *Waiting changes*: interactive waits appear only in the line;
  they expire after 7 days.
- **Problem:** Ada asks from her phone and locks it. "Waiting for you: close 2
  duplicates" then sits in a conversation she may not reopen, and it expires
  silently.
- **Fix:**
  - A waiting change still undecided when Ada leaves that conversation becomes one
    "Needs you" item: "Your assistant wants to close 2 duplicates · [ Apply ] [ Review ]".
    It is filed under Inbox *Questions*.
  - An expired item leaves one line in Recent: "Expired: close 2 duplicates · Ask again".

**P2-5. The wrong person approves a "page someone else is typing in", and "Apply" is a generic verb.**
- **Where:** AST-5 always-wait rule 4, and the reaction "draft a reply".
- **Problem:**
  - The conflict is with Jonas's typing, not with Ada's consent. When Ada taps
    Apply while Jonas still types, it fails with "Changed since you asked".
  - A drafted reply waits for "Apply", which is not how a messenger sends things.
- **Fix:**
  - Rule 4 becomes deferral: "I'll edit *Suppliers* when Jonas finishes typing." It
    applies automatically if the version still matches when the session ends; if
    not, it becomes a normal waiting item.
  - Waiting items use the object's own verb: *Send*, *Close*, *Remove*, *Hand off*.
    *Apply* stays only for mixed batches.
  - The draft reply opens in the Inbox mention's existing **Reply**, prefilled, with
    "Drafted by your assistant" and **Send**.

**P2-6. Suggestions to others interrupt them without Ada choosing to.**
- **Where:** Journey 6, row "Outside her rights": "Jonas owns #8, so I suggested the change
  to him".
- **Problem:** Ada's request puts an item in Jonas's Inbox. That contradicts the design's
  own anti-pattern, "Interrupting people the owner did not ask it to contact".
- **Fix:** "Jonas owns #8. Suggest this change to him? [ Send to Jonas ]". The suggestion
  is prepared, waits for Ada, and reaches Jonas only after one tap.

**P2-7. Undo gives up too easily, and its wording varies.**
- **Where:** AST-6 Undo, the Journey 3 Undo rule, and "Result lines".
- **Problem:**
  - "Changed since. Open it" fires when *anything* on the object changed. A
    rename becomes impossible to undo the moment someone moves the task to In
    progress, which happens constantly in an active project.
  - The line says "Undo" when done and "Undo all" when stopped.
  - A partial Undo all has no copy.
- **Fix:**
  - Undo restores only the fields the assistant changed, if those fields are
    untouched.
  - The line always says **Undo** (meaning all of it). Each item in the expanded
    list has its own Undo.
  - Partial result: "Undid 5 changes. 2 changed since: #4, #7 · Open".

**P2-8. Background work can flood a shared stream.**
- **Where:** AST-7, *Output*: "Changes appear as ordinary notices in their project", and
  the "Every hour while I work" option.
- **Problem:** An hourly project job can post 8 notices a day into a conversation that
  colleagues share.
- **Fix:**
  - "Done: nothing to change" never posts in a shared conversation.
  - A job's notices fold into its previous notice while no person has posted since
    (S8): "Ada's assistant · Hourly tidy · 6 changes today ⌄".

**P2-9. "Reaction" means an emoji in a messenger, and "job" is jargon.**
- **Where:** The assistant screen: "+ New reaction", "+ New scheduled job", and the
  *Scheduled* header.
- **Fix:**
  - Use parallel section headers: **On a schedule** and **When something happens**.
  - Each section's button is **+ Add**, and its sheets are titled "On a schedule" and
    "When something happens".
  - Keep "reaction" and "job" internal only. Add both words to the AST-10.2
    banned-word scan.

**P2-10. The hand-off picker treats other people's assistants inconsistently.**
- **Where:** Journey 2 says other people's assistants are not in the `@` list. The S12
  picker on the canvas lists people's agents with "asks Jonas first".
- **Problem:** Jonas's picker would show "Ada's assistant", but F-019 forbids his action
  from starting it, and nothing defines what he sees.
- **Fix:** Jonas sees "Ada's assistant · for Ada · asks Ada first". Choosing it sends
  Ada one Needs-you item: "Jonas asks your assistant to do #10 · [ Allow ] [ Not now ]".
  Allow is Ada's action, so F-019 holds and the canvas pattern stays symmetric.

**P2-11. "Yours" is defined but never shown, and two of its cases surprise colleagues.**
- **Where:** *Terms*, "Yours" (decision text): "a task you created … a Wiki page … you or
  your assistant created".
- **Problem:**
  - A task Ada created but Jonas is responsible for counts as Ada's, so the
    assistant may rename or close Jonas's work without asking.
  - A page Ada started but Jonas mostly wrote counts as Ada's.
  - The user never sees the rule, so "other people's things" cannot be predicted.
- **Fix:**
  - A task is yours if you are responsible for it, or you created it and nobody
    else is responsible.
  - A page is yours if nobody else has edited it.
  - The *Can* sentence and the ready card say: "It asks before changing things
    other people made or are responsible for."

**P2-12. Several failure messages are vague, and "Try again" can double the work.**
- **Where:** Journey 6 and AST-9.
- **Fix:**
  - Replace "Limit reached" with the limit's name: "I stopped after 5 minutes, the
    limit for one request. I made 4 changes · Undo · [ Continue ]".
  - Vendor down after partial work: "Claude stopped answering after 2 changes ·
    Undo · [ Finish it ]". *Finish it* continues with the list of changes already
    made, so it does not redo them.
  - Add a row for the change limit: "I made 20 changes, the most for one request. 6
    more wait for you · Review".
  - For "No free place" and "Subscription sign-in off", add `[ Tell whoever runs
    Flux ]` next to the API key choice. For most people, the API key is not a real
    option.

**P2-13. The first-run consent and risk notes need small corrections.**
- **Where:** Journey 1 steps 1–4, and the AST-2 note in the *New scheduled job* sheet.
- **Fix:**
  - The ready card adds "Others in the conversation see what you ask it and what it
    does." (This is O-008's "who sees answers".)
  - When the runtime is off, the Home card and the "Which do you use?" sheet do not
    promise "the plan you already have". They show only the choices that work here.
  - Show the background note once per account, not once per job. Shorten it to:
    "Runs on your Claude plan while you're away. Anthropic may limit this use
    without notice. If your plan says no, it skips that time and tells you." After
    that, the sheet shows one meta line, "Runs on your Claude plan".

### P3: polish

- **Inbox "Unblock" collides with the reaction "try to unblock it".** The canvas Inbox
  has an **Unblock** button that clears the blocker. Rename the action to "→ add next
  steps", which says exactly what it does.
- **Limit wording.** "Runs per day" and "changes per run" become "Requests a day" and
  "Changes per request". Journey 6 already says "requests".
- **Recent and Activity.** The canvas agent page uses **Recent**. Use "Recent ›" on the
  assistant screen too, not "Activity · today: 4 changes".
- **Device names.** "It starts when your laptop is on" uses the connection's device
  label: "…when *Desk laptop* is on".
- **Handing off to Jonas's Codex.** Replace "Waiting for you: hand #8 to Jonas's Codex.
  Jonas needs to agree." with "Jonas has to agree to hand #8 to his Codex. [ Ask Jonas ]".
- **One tap to allow and retry.** "Allow Wiki edits" and "Try again" become one button,
  `[ Allow Wiki edits and try again ]`.
- **Pause from the assistant's panel.** Add "Pause my assistant" to the panel's ⋯ menu,
  plus "Manage ›". Turning it off then takes 2 taps from anywhere, not 4.
- **GitHub event.** Offer "a PR is ready on my task" only in projects linked to GitHub,
  and word it "a pull request is ready on my task".
- **Set-up prompts.** The Home "Meet your assistant" card gets ✕ / "Not now". The `@`
  list's "My assistant · Set up" moves to the end after it has been dismissed once.
- **Operator-trust note.** Show F-022's note only when someone else runs this Flux:
  "Jonas runs this Flux and could technically reach your sign-in. Sign in only if you
  trust him."
- **Undoing a created Wiki page.** The Undo result says what happens: "Moved to your
  drafts".
- **Replies in a thread.** Ada's reply in the thread of her assistant's message addresses
  it without `@`.
- **Agents tab state.** The project Agents row for the assistant uses the result-line copy
  for its state: "Working… reading 14 tasks" or "Waiting for you · close 2 duplicates".
- **Screen readers.** The working line and result line announce politely ("Ada's assistant
  finished: renamed 3 tasks").
- **Offline.** An `@My assistant…` sent while offline shows "Sends when you're back", as
  photos already do. Stop, Undo and Apply show "Offline" rather than failing.
- **API credits hint.** Be honest about the effort: "Use them for background work
  instead (about 5 minutes on console.anthropic.com) ›".
- **First starter chip.** "Tidy this project's tasks" is vague, and in a shared project
  it starts with edits colleagues will see. Lead with "( Catch me up )", then "( Turn
  this thread into tasks )".

## Delight that adds no complexity

1. **The assistant writes the Home greeting line.** This is P1-3's placement: the single
   most visible daily proof that it works.
2. **Set up a schedule by asking.** "@My assistant every weekday at 9 tell me what needs
   me" prepares a job that waits: "Ready: *Morning summary*, weekdays 9:00 · [ Turn on ]".
   The owner's tap is still what enables it, so the rule that no run creates a job holds
   in substance.
3. **"Do it at 14:00"** next to "Remind me at 14:00" when the plan limit resets. It runs
   the same request once, as Ada's own scheduled request.
4. **Kreska's "Waiting for you" expression** (eyes on the composer) on the assistant's
   message while it has waiting items. The expression already exists.
5. **"Next:" in the panel's Now** when idle: "Next: morning summary tomorrow 9:00".

## Keep as is

- The two-option **"Do it and tell me | Ask me first"** control, with a single sentence
  of what always waits under it.
- **Five switches in everyday words**, with *Only read*, projects and limits folded
  under *More*. There is no permission matrix.
- The result-line state vocabulary: *Done, Waiting for you, Suggested, Stopped after N
  changes, Paused, Skipped, Undone by Ada*.
- Journey 6's rule: say what happened, say whether anything changed, and offer one next
  step in the same line. Nothing ever falls back to another account.
- **Stop** refuses the next call at once and keeps the list ("Stopped after 3 changes ·
  Undo").
- Activity attribution with the quoted request: "renamed this · asked by Ada: 'tidy
  this project's tasks' · Undo".
- The **Can** sentence, generated from the switches and identical in the panel and
  hand-off step 2.
- Asking via the S14 question card, not by guessing.
- Background runs: missed runs are skipped ("Skipped: Flux was off at 9:00"), three
  failures pause the job with one Inbox item, and runs are never more than hourly.
- Reactions built from two pickers over a fixed set. "Tell me" folds into the existing
  Inbox item, with no second notification.
- Hand-off to your own Codex with "Codex is offline. It starts when…", and *Allow*
  reusing hand-off step 2.
- Empty-state starters that take two taps, and the truthful working line ("reading 14
  tasks").
- The anti-pattern list, and the AST-10.2 banned-word scan. Extend the scan with
  "job" and "reaction".
